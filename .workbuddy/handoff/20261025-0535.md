## 2. 议题一：shared 的构建顺序（本会话要裁决的核心）

### 2.1 五条实测事实

1. **`packages/shared/dist/` 未入库**（`.gitignore` 的 `dist/` 命中），但本地存在且结构完整：`dist/esm/*.js + *.d.ts`、`dist/cjs/*.js`、两份目录各有 `package.json` 模块类型标记（`scripts/postbuild.mjs` 生成）。
2. **三处消费面的解析口径不一致**——这是全部麻烦的根源：

   | 消费面 | 解析到 | 现状 |
   |---|---|---|
   | `tsc -p tsconfig.json`（typecheck） | `shared/src`（`paths`） | 通过，**不依赖 dist** |
   | jest（`moduleNameMapper`） | `shared/src` | 通过，**不依赖 dist** |
   | `tsc -p tsconfig.build.json`（server build） | `shared/src`（继承同一 `paths`） | **只要 import 就 TS6059** |
   | Node 运行时 `require('@wo/shared')` | `dist/cjs/index.js`（`exports.require`） | 需要 dist 存在且新鲜 |

   即：**类型走源码、运行走产物，两套口径并存**。当前之所以没炸，只是因为 server 的运行期闭包还没引 `@wo/shared`（唯一引用它的 `apps/server/src/index.ts` 被 build 显式 exclude）。

3. **实测 TS6059**：在 `apps/server/src/` 放一个 `import { SHARED_PACKAGE_NAME } from '@wo/shared'` 的文件，跑 `tsc -p tsconfig.build.json --noEmit` → **exit=2，报 3 条 TS6059**（`shared/src/index.ts`、`utils/fnv1a32.ts`、`license/sm2-constants.ts` 均不在 `rootDir` 下）。P3-011-02 记录里预警的正是这一段。
4. **实测可行解**：把 `tsconfig.build.json` 的 `paths` 覆盖为 `["../../packages/shared/dist/esm/index.d.ts"]` → **exit=0**。且该 `.d.ts` 内部含 `.js` 后缀的相对 import（`./utils/fnv1a32.js`），Node10 也能正确解析到同级 `.d.ts`——**这条路已验证可用，不是推断**。
5. **实测否决项**：摘掉 `paths` 吃 `exports` → **exit=2 / TS2307**，TS 自述「could not be resolved under your current 'moduleResolution' setting」。与 ANCHORS §2 P3-010-03 记录完全一致（server 段是 `Node10`，不认 `exports`）。
6. `esbuild` **不在依赖树**；且 Nest 依赖 `emitDecoratorMetadata`，esbuild/tsup 默认不支持 → 打包器方案成本高，不建议。

### 2.2 决策轴

不是「用 src 还是用 dist」——**这个问题实测已有答案**（build 期必须吃 dist 声明，否则 TS6059）。真正要裁的是：

> **谁保证 `dist` 在 server build 之前已经是最新的？**

三个子问题：
- (a) 顺序由**脚本字面串联**保证，还是由**工具（`tsc -b` 项目引用）**保证？
- (b) 要不要加「dist 新鲜度」门禁？若要，用 mtime 还是内容哈希？
- (c) `verify` 目前**不含 build 段**（ANCHORS §2 明确写「检查命令里没有 build 步」）——所以「verify 10/10」**不证明可构建**。要不要加？

### 2.3 候选方案

**A 案（改动最小，已实测）：build 期类型吃 dist 声明，顺序由脚本字面串联**

- `apps/server/tsconfig.build.json` 覆盖 `paths` → `packages/shared/dist/esm/index.d.ts`
- `tsconfig.json`（typecheck）与 jest **保持指向 `src`**，开发期零 build 依赖、反馈最快
- 根 `build` 脚本改为显式三段串联：`shared(esm) → shared(cjs) → postbuild → server`（沿用 §0「显式枚举优先、不嵌套 pnpm」的既有风格）
- 顺序是**构造性保证**（字面先后），不靠检查兜底 → 不用写新鲜度门禁
- 代价：`pnpm --filter @wo/server build` 单独跑时仍可能吃到旧 dist；故 `apps/server` 的 `build` 脚本宜改为「先 shared 后自己」，或文档约定只从根入口 build
- 遗留：web 侧同型问题（`apps/web` 目前无 build 脚本，P3-030 加 Vite 时会撞同一堵墙，届时同一套办法）

**B 案（更彻底，未验证）：TypeScript 项目引用 `composite` + `tsc -b`**

- 顺序由 TS 自动按依赖拓扑保证，不需要任何新鲜度门禁
- 成本：shared 需 `composite: true`；但它有两套输出（esm/cjs），composite 只能挂在其中一份（esm），cjs 那份仍须独立 `tsc -p` 先跑——**顺序并未完全消失**，只是从「全人工」变成「半自动」
- 与 Nest 装饰器 + `isolatedModules` + `declarationMap` 的组合**未实测**，有踩坑预算
- 不引新工具，与 ADR-005「最小构建面」不冲突

**C 案（否决）：`dist` 入库**
消灭顺序问题，但脏 diff + 双份真相（src 与 dist 都可能被改）+ **直接推翻 ANCHORS §2 那条裁决的前提**（「dist 未入库，故检查命令里不能有 build 步」）。等于改写既有裁决，不建议为省事走这条。

**D 案（否决）：打包器内联 shared**——esbuild 不在树 + `emitDecoratorMetadata` 不支持，Nest DI 会失效。

**E 案（备选）：server 改 `moduleResolution` 到 `Node16`/`Bundler` 后摘 `paths`**——理论上最"正统"，但同样要改 ANCHORS §2 既有裁决，且 Node16 + CommonJS + 双格式依赖的互操作有坑。留作 A 案失效时的退路。

### 2.4 建议

**取 A 案，顺序由根 `build` 脚本字面串联保证，不加新鲜度门禁**。理由：唯一已被实测证明可行（exit=0）、改动面最小（3 个文件）、保住「typecheck 不需要 build」这条开发期最重要性质；而「顺序」这类问题应当用构造性手段消灭（字面先后），而不是再加一个检查脚本去追（检查脚本本身就是新的自洽缺口）。

若用户要求更强保证，则升级到 B 案而非加 mtime 门禁；若坚持加门禁，用**内容哈希**（写 `dist/.srchash`），不要用 mtime（内容未变的 touch 会误报）。

**裁决定案后必须做的两件事**：
1. 结论落 `docs/phase3/ANCHORS.md` §2 决策表（新增一行，带反向验证），版本号 +1
2. 若改了 §2 既有裁决（如 C/E 案），须先登记 `docs/decisions/OPEN-DECISIONS.md` 并说明为何推翻

- **依赖**：`P3-011-02`（已完成，已满足）

### 3.2 开工前必须解决的三个缺陷（否则这包会"全绿但无效"）

**缺陷 1（最严重）：`additionalProperties:false` 这条断言零判别力**

实测（zod 4.6.7，包内跑）：

| 写法 | 输入含未知键 `{a,b}` | `toJSONSchema().additionalProperties` |
|---|---|---|
| `z.object({a})` | **success**，`b` 被静默剥离，data=`{"a":"x"}` | **`false`** |
| `z.strictObject({a})` | **fail**，issue code = `unrecognized_keys` | `false` |

→ **两者输出完全一样**，断言无法区分 strict 与 strip。后果：`-03` 全用 `z.object` 也能 100% 全绿，但 `-04` 要求「body 未知键 → 400 + 7001」时必红（`z.object` 根本不报错，只会偷偷丢字段）。
**修法**（二选一或并用，建议并用）：
- 断言升级为行为断言：对每个 object schema 注入未知键 → `safeParse` **必须失败**且 `issues[0].code === 'unrecognized_keys'`
- 静态约束：`packages/shared/src/schemas/` 内禁用裸 `z.object(`，只允许 `z.strictObject(`（与 `-05` 计划的 `request-schema-strict.js` 规则**合并口径**——注意该规则原定扫描 `apps/`，需扩展到 `packages/shared/src/schemas/`）

**缺陷 2：「请求 9 + 响应 13」与实测不符**

实测 22 个名字对得上总数，但按引用方向拆分是 **8 + 12 + 2**：

- 仅被 `requestBody` 引用（8）：`LoginRequest`、`RefreshRequest`、`UserCreateRequest`、`UserUpdateRequest`、`SsoCallbackRequest`、`FileCreateRequest`、`FileRenameRequest`、`ShareCreateRequest`
- 被 paths 的 `responses` 引用（12）：`Error`、`LoginResponse`、`RefreshResponse`、`UserResponse`、`UserAdminResponse`、`SsoConfig`、`FileResponse`、`FileListResponse`、`SnapshotResponse`、`ImportTaskStatus`、`ShareResponse`、`AuditLogListResponse`
- 仅被父 schema 内嵌引用（2）：`ValidationErrorDetail`（被 `Error.detail` 引，openapi 第 1204 行）、`ValidationErrorItem`（被 `ValidationErrorDetail.errors.items` 引，第 1217 行）

→ 9/13 这个拆分口径**无法从 openapi 机械复现**。开工前需按 **D1-13 卡**（本会话读不到，需用户提供）确认真实定义；`check-schema-names.mjs` 的断言里**不要写死 9/13**，应只断言「22 名集合双向相等」，把 9/13 降级为说明性注释。

**缺陷 3：`check-schema-names.mjs` 不存在**

台账断言直接引用了它，但 `scripts/` 下没有此文件。需在本包内新建（参考 `scripts/check-endpoint-groups.mjs` 的写法：解析失败即 fail，不要用空结果冒充零缺失）。

### 3.3 写作约束（不遵守会直接 build 失败）

1. **相对 import 必须带 `.js` 后缀**：`tsconfig.build.esm.json` 开了 `verbatimModuleSyntax: true`，specifier 原样输出到 ESM 产物，缺后缀 Node ESM 运行时 `ERR_MODULE_NOT_FOUND`。现有 `src/index.ts` 即写作 `from './utils/fnv1a32.js'`。
2. **`exactOptionalPropertyTypes: true`**：可选字段不能写 `field?: string` 又赋 `undefined`，需 `field?: string | undefined` 或省略。
3. **`noUncheckedIndexedAccess: true`**：索引访问结果类型含 `undefined`，数组/record 取值需判空。
4. **shared 的 import 禁令**（P3-001 §5.3）：禁 React / Nest / univer / yjs，禁原生依赖，禁 side-effect。`dependencies` 只允许 `zod` + `sm-crypto`（依赖面门禁 G/D 段会抓）。
5. **两条自定义 lint 规则对 `packages/shared/src` 生效**：`wo/no-emoji`（注意 U+2194 一类"看起来不像 emoji"的符号也会被抓，P3-011-02 已踩过一次）、`wo/no-hardcoded-color`。
6. **schema 落在 `src/schemas/` 后无需改共享构建配置**：`build.esm/cjs` 的 `include` 都是 `src/**/*.ts`，新文件自动进构建；但**必须记得构建**，否则 `dist` 陈旧（见 §2.2(a)）。
