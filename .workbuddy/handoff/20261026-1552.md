### 2.1 由上面推出的两条断言，比任务卡里写的更硬

**推论 A｜滚动不会弄脏自动保存，也不会产生一次写。**
`ScrollCommand` 是 `CommandType.COMMAND`，会触发 `onCommandExecuted` → `SheetHandle.onChange` →
`autosave.notifyChange()`；但快照内容没变，`autosave.ts:135` 的 `hash === lastHash` 会命中
`save:skip`。**所以 `--restore` 段可以放心地断言「全程 `save:end` 恰好 0 次」**——
若哪天出现 1 次，说明滚动被写进了快照（与 1.2.0 事实矛盾），这条能当升级回归的探针用。
反过来：任务卡若只断言「④ 视口恢复了」，就无法区分「恢复成功」与「滚动顺手存了一份脏文档」。

**推论 B｜别指望 `save()` 快照能恢复视口。** 快照里的 `scrollLeft/scrollTop` 永远是**输入值原样**
（我们的 `seedDoc` 根本没写这两个字段），引擎也不会应用到视图上。所以「视口存 localStorage」
不只是审美选择，是唯一可行路径——对方卡 §2 的决策与这条互为旁证。

### 2.2 一个会让人误判「已经恢复了」的坑

`ScrollCommand` 的兜底写法是：

```js
sheetViewStartRow: sheetViewStartRow ?? currentRow ?? 0 + ySplit,
offsetX: offsetX ?? currentOffsetX,
```

`?? 0 + ySplit` 是**优先级怪相**（本意 `(0) + ySplit`）。危险不在这个怪相，在 `??`：
**漏传 `offsetX/offsetY` 不会报错，会静默沿用当前值**。重载后当前值就是 0，
于是表现为「行列对了、像素差了」——画面看着像恢复成功。
→ 实现时必须**四个字段一次全传**；判据必须**逐字段比**（任务卡 §5.1 ④已这么写，保持住）。

另：`getScrollState()` 的 facade 签名是非空 `IScrollState`，但 `FWorkbook.getScrollStateBySheetId()`
返回 `Nullable`。**首帧前 render unit 还没注册，别信非空签名**，要 try/catch 兜住（对方
`readScrollState` 已经这么写了，别被「类型说非空」的直觉改回去）。

## 3. 我对 `--restore` 判据的一处建议（会偶发假绿）

任务卡 §5.1 ② 是「视口状态已写入 localStorage」。但探针**不清 localStorage**（见 §2 表末行），
上一轮运行留下的 `wo.view.wo-demo-book` 会残留。若某次运行预设的视口恰好与残留值相同，
**② 会在「本次根本没写」的情况下也绿**——这正是 V2.2 踩过的「判据抢跑」同型错误
（`tasks/V2.2.md` §5：偶发红的判据等于没有判据，偶发绿的更坏，因为它不报错）。

两个修法，任选：

- 探针开始处把 `storageTypes` 改成 `'indexeddb,localstorage'`（一行）；
- 或 ② 之前先写一个**不可能出现的**哨兵值（如 `sheetViewStartRow: -1`，`readViewState` 会判非法而返回 null），
  再断言读到的是本次写入的正值。
