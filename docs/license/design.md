## 1. 审查缺陷与修法

**缺陷**：单源指纹（CPU+主板序列号哈希）在虚拟化/云平台场景失效——vCPU 无稳定序列号、容器环境主板信息同质，导致合法客户 License 验签失败（误杀）或整机漂移被攻击者利用（换台机器重算指纹即绕过）。

**修法（本文件定义）**：多源加权指纹 + 匹配阈值容忍单项漂移 + 离线换绑申请流程。

## 2. 多源加权指纹

### 2.1 采集源（N=6，按可得性降级采集）

> 本表为**物理机/虚机直装形态**权重；Docker 容器交付形态见 §2.1-b 专用权重表（P0-2 修订）。

| # | 采集项 | 采集方式（Node，无原生依赖优先） | 虚拟化/容器下的表现 | 权重（直装） |
|---|---|---|---|---|
| 1 | 主板/产品序列号 | dmidecode（Linux，需 root）/ wmic（Windows），DMI 表 | KVM 常为空或 "None"；容器内 /sys/firmware 不可见 | 0.25 |
| 2 | CPU 型号 + 核数 + 频率特征 | /proc/cpuinfo 或 os.cpus() 聚合哈希 | 稳定（同宿主机同型号稳定） | 0.15 |
| 3 | 磁盘序列号（系统盘） | lsblk/blkid 或 wmic diskdrive | 云盘有序列号但重建实例会变 | 0.20 |
| 4 | 主网卡 MAC | os.networkInterfaces() 首物理网卡 | 容器下可能是 veth（弱信号） | 0.10 |
| 5 | 机器名 + OS 内核版本指纹 | os.hostname + os.release | 客户通常不改；**Docker 默认 hostname 为随机短 ID，容器重建即变** | 0.10 |
| 6 | 部署特征盐 | 安装时生成、存于**持久数据卷**的随机 salt（.machine-salt） | 随数据卷持久，容器重建不漂移 | 0.20 |

采集失败（权限不足/字段为空）的项记为 absent，不参与匹配也不计入分母——防止「字段缺失导致总分永远不达标」的误杀。

### 2.1-b 容器部署形态专用权重表（P0-2 修订，v1.2）

**矛盾背景**：交付形态是 Docker 容器（Spec §4），但 dmidecode 需 root 且容器内 /sys/firmware 不可见、Docker 默认 hostname 随机短 ID 且容器重建即变——按直装权重表，客户现场会大面积 absent 或重建漂移，匹配 < 0.70 大面积激活失败，换绑额度（2 次/年）根本不够烧。

**裁决方案（方案②容器内自适应为主）**：安装时检测部署形态（存在 /.dockerenv 或容器环境变量），命中即按本表采集与判定：

| # | 采集项 | 容器内可得性 | 权重（容器） | 说明 |
|---|---|---|---|---|
| 6 | 部署特征盐（持久数据卷） | 可得（数据卷挂载是交付前提） | **0.40** | 升主权重：数据卷是容器形态唯一既持久又防漂移的源 |
| 2 | CPU 型号 + 核数特征（/proc/cpuinfo 容器内可见） | 可得 | 0.20 | 宿主机同质时弱信号，但不漂移 |
| 3 | 磁盘序列号（数据卷宿主盘） | 视挂载方式可得 | 0.20 | absent 时不入分母 |
| 4 | 主网卡 MAC | 常为 veth | 0.10 | 弱信号保留 |
| 1 | dmidecode 主板序列号 | **不可得（无特权容器）** | 0.00 | 降级为可选增强：仅特权容器部署时参与（加回 0.15，其余项等比收缩） |
| 5 | hostname + 内核指纹 | **剔除** | **0.00** | 容器形态下强制权重 0 且不参与指纹合成——防容器重建 hostname 漂移误杀 |

**容器形态判定规则调整**：
- 匹配阈值保持 >= 0.70（分母只含非 absent 且权重非 0 的项）；
- **关键项改为「#6 卷级盐必通过」**（直装形态关键项规则不变：主板或磁盘至少一项）；
- 防搬运语义变化：容器形态的指纹唯一性主要由卷级盐承担（salt 文件权限 0600 + 随数据卷持久），整机镜像分发场景靠「新部署无盐 → 首次安装生成新盐 → 旧 License 指纹不匹配」阻断。

**方案①（宿主机 agent，后续增强路径，不进 MVP）**：systemd 服务以 root 在宿主机运行采集器，一次性采集 DMI/磁盘序列号写入数据卷固定 JSON（0600），容器内读该文件参与匹配——可恢复直装级权重强度，但引入宿主机组件增加交付与运维复杂度，登记为 v2 增强项，MVP 不做。

### 2.1-c 拷卷即过与兜底失效的显式承认（v1.4，外部评审分支 D 修订）

**实证链（评审人推理，全部引自本文件自身条款）**：容器形态下 #6 卷级盐是唯一关键项（§2.1-b 判定规则）且 0.40 主权重——**复制数据卷 = 复制 License**（盐随卷走，其余项弱信号或 absent）；§2.2 给的兜底「席位并发检测」在 §4-bis 下为**进程内 Map、单写者单实例**——克隆体是独立部署（独立进程/独立库/独立 Map），彼此结构性不可见。**席位并发兜底对跨实例克隆失效，该承诺作废**（§2.2 与 §5.3 中「席位并发检测告警兜底」表述自 v1.4 起废止）。

**路线裁决（A/B/C，team-lead 代 PM 裁决，PM 复核待限额恢复）**：采 **A——接受「技术不防克隆」，License 定位为「授权计量与合规凭证」，不承诺防拷贝**。理由：①政企私有化场景的真实对手是等保审计与年度授权复核，不是盗版商；②为防克隆把方案①宿主机 agent 提前进 MVP，需在鲲鹏+麒麟双架构多维护一个 systemd 宿主组件，破坏容器交付简易性与信创适配面，性价比明显为负；③信创三种最常用交付路径（虚机模板克隆/整机镜像分发/整卷备份恢复）全是带卷复制——技术拦截与交付形态正面冲突。B 否决（成本实数：宿主 agent 需适配麒麟 V10 + 统信 UOS 双 OS × x86_64/aarch64 双架构四象限的 systemd 打包与权限联调，交付与运维复杂度显著上升，v2 再评估）；C 的「集中上报」在离线私有化下无技术通道，其唯一可操作形态（审计导出比对）已并入 A 的配套③，不单列路线。

**配套三件事（与路线裁决同时生效）**：
1. **商务强制披露**（见 §6-bis，对齐席位口径 v1.3 先例）；
2. **时钟回拨检测 + 过期宽限**（见 §2.4）；
3. **SM2 启动断言**（见 §2.5）。

### 2.2 指纹合成与匹配

```
machine_fingerprint = SM3( concat( item_1..item_6 各自 SM3 后的定序拼接 ) )  // 申请码中的指纹摘要
匹配分数 = Σ(通过项权重) / Σ(非 absent 项权重)
```

- **通过判定**：匹配分数 >= 0.70 且关键项（#1 或 #3 至少一项）通过；
- **容忍单项漂移**：换网卡（#4 变）、升内核（#5 变）不触发失效——单项漂移最多损失 0.10~0.25 分，0.70 阈值下可容忍 2-3 项漂移；
- **防整体搬运**：#6 部署特征盐**防误装与随手拷贝安装目录**（把应用目录复制到另一台机器，盐随目录走但其余硬件项全变，匹配不过）——**不防整盘克隆**（盐随数据盘被一并克隆）。整盘克隆场景依赖关键项校验（虚拟化下 #1 常为 absent、#4 为 veth 同前缀，关键项不达标即拒；容器形态下关键项=卷级盐必通过）——~~席位并发检测兜底~~（v1.4 废止：席位计量为进程内单实例，对跨实例克隆结构性不可见，见 §2.1-c）；
- License 文件内记录**申请时的分项哈希快照**（非明文），安装验签时逐项比对后按上式计算分数。

### 2.4 时钟回拨检测与过期宽限（v1.4 新增，外部评审分支 D P1 修复）

**问题**：`expiresAt` 判定依赖系统时钟——①回拨（改系统时间到过去）可无限续期；②前跳（NTP 一次校正/运维误设）即误判过期→全员只读。内网信创环境 NTP 常不可用，两个方向都会真实发生。原文档 141 行零覆盖。

**机制（三层）**：
1. **已见最大时间戳持久化**：licenses 表新增 `max_seen_at` 列（timestamp，应用层维护）——每次 License 校验（登录/WS 握手/周期复验）后以 `max(当前时间, max_seen_at)` 更新；**判定有效期时取 `max(系统时钟, max_seen_at)`**——回拨后系统时钟小于 max_seen_at，仍按 max_seen_at 判定，改时间无法续期；
2. **回拨告警不误杀**：检测到 `系统时钟 < max_seen_at - 24h` 时**不拒绝服务**，仅写审计日志（action: license.clock-rollback，detail 含偏差量）+ 管理后台状态提示——政企现场时钟错乱是常见运维事故，误杀风险必须压住；偏差 ≤ 24h 视为正常校时静默容忍；
3. **过期宽限期 7 天**：`expiresAt < now` 后**维持只读 7 天**（AC-09 降级语义不变），期间状态栏显示「License 已过期，宽限期至 X 日，请联系供应商续期」；宽限期计算同样取 `max(系统时钟, max_seen_at)` 防回拨绕过；超 7 天维持只读不锁死（登录/查看可用，编辑禁用——与 AC-09 三层防线一致，不存在「锁死」态）。**与 AC-09 的关系**：AC-09「过期降级只读」口径不变，宽限期不改变降级行为，只改变**提示语义**（从「已过期」变为「已过期+宽限倒计时+续期引导」），给客户续期操作留窗口。

### 2.5 国密能力启动断言（v1.4 新增，外部评审分支 D 实证采纳）

**问题**：SM2 签名是 License 验签核心，但既有启动断言只查 `crypto.getHashes().includes('sm3')`——发行版 Node 若链 OpenSSL 1.1.1 或裁剪版，症状是「启动不报错、激活时静默失败」，最难现场定位。

**断言三级（探针 `scripts/gm-crypto-probe.mjs` 固化，评审人产出已收编）**：
- G1 摘要 sm3 存在（getHashes）；
- G2 曲线 SM2 存在（getCurves）；
- G3 **SM2 自签自验真跑一次**（generateKeyPairSync('ec',{namedCurve:'SM2'}) → createSign('sm3') 签名 → createVerify 验签）——任一失败**拒绝启动**；
- G4 sm4 六模式（sm4/sm4-cbc/sm4-cfb/sm4-ctr/sm4-ecb/sm4-ofb）与 G5 PBKDF2-HMAC-SM3 进 CI 门禁**不进启动断言**（License 链路 MVP 用不到 sm4；PBKDF2 已由登录链路自然验证，启动多跑 10 万轮派生浪费 ~60ms）。

**实跑基线（2026-10-21，win32-x64，Node 22.22.2 / OpenSSL 3.5.5）**：G1-G5 全 PASS（G3 sig=70B、G5 58ms@10 万轮）。**鲲鹏 aarch64 官方二进制复测列入 Phase 3 首迭代验证项**（与 PBKDF2 延迟实测同批）。

## 3. 离线换绑申请流程

虚拟机迁移、硬件维修等场景触发换绑（匹配分数 < 0.70）：

```
客户内网                                  供应商（离线）
   |                                        |
   | 1. 管理员在后台点「申请换绑」            |
   |    POST /license/activate-request      |
   |    返回 requestCode =                  |
   |    {旧LicenseId, 新机器指纹, 申请时间,  |
   |     操作员} 经 SM3 摘要防篡改           |
   |--------------------------------------->| 2. 线下交付（邮件/光盘随交付包）
   |                                        |    供应商私钥签发换绑 License
   |                                        |    （同席位同有效期，指纹=新机器，
   | 3. POST /license/install               |     revoke 旧指纹）
   |----------------------------------------|
   | 4. SM2 公钥验签 + 新指纹写入            |
   |    旧指纹行标记 revoked（licenses 表   |
   |    status='revoked'，历史行保留；      |
   |    active 唯一性由应用层校验，见下）   |
```

**active 唯一性实现约束（复审打回 2 修订）**：
- licenses 表**不建** database 层 unique(machine_fingerprint) 索引——历史行（含 revoked）与新激活行可能同指纹（客户维修后换回旧机器），DB 唯一约束会阻断合法换回；
- 唯一性改为**应用层校验**：激活/换绑安装的事务内查询「该 machine_fingerprint 是否存在 status=active 的行」，存在则拒绝（错误码 5002 语义）；不使用部分唯一索引（partial unique index）——国产库对 WHERE 谓词索引的兼容性存疑，规避。

约束：
- 换绑次数写入 License 声明上限（默认每自然年 2 次，供应商可调），防止「换绑流程被用作席位倒卖通道」；
- 旧 License 指纹 revoked 后，同一 License 文件在新旧机器上均不可激活（active 行唯一性校验）；
- 换绑审计：申请与安装均落 audit_logs（action: license.rebind-request / license.rebind-install）。

## 4-bis. 席位口径与并发计量（终版，PM 商务备案 2026-10-21）

- **席位 = 并发「编辑会话」去重用户数**（user_id 去重；同用户多标签/多文件计 1 席）；**查看会话不占席**；
- 超席行为：新 edit 连接自动降级 view（提示可显示），已有编辑会话不中断；view -> edit 升级走 WS [ROLE_UPGRADE] 帧，服务端判席后 ack/reject，**升级瞬间占席**（防「先 edit 后补占」绕过窗口）；
- 60s 断线宽限：编辑用户断线 60s 内重连不重复占席；
- 计量实现：**进程内**（单写者单实例 Map 计数，不引入 Redis——Redis 属 ADR-004 扩容范畴，届时段控制与席位计量统一设计）；
- licenses 表 `peak_concurrent` 列记录历史峰值（连接建立创新高即更新），`GET /api/v1/license/status` 暴露 currentConcurrent/peakConcurrent；完整峰值统计报表列 **P1 不进 MVP**（防范围膨胀）；
- 实现细节锚点：openapi x-websocket（连接角色/席位判定/ROLE_UPGRADE 帧/4410 与席位口径关系）。

**商务备注（PM 要求，任务 4）**：销售物料须显性标注席位口径——「并发编辑用户数，查看不限」，防止与 WPS 等「注册席位」计费口径混淆产生商务纠纷。

## 6-bis. 防拷贝口径商务强制披露（v1.4 新增，team-lead 代 PM 落，PM 复核待限额恢复）

**背景**：本文件 §2.1-c 已显式承认容器形态「拷卷即过」（技术不防整盘克隆）。若销售在投标/合同/宣传材料写「一机一码、防拷贝、防克隆」，属**虚假承诺**——政企项目可追责。对齐席位口径 v1.3 先例，强制披露如下：

**投标/销售物料允许写**：
- 「离线授权、SM2 数字签名防篡改、席位与有效期计量、换绑流程支持硬件迁移」
- 「License 为授权计量与合规凭证，配合审计日志支持年度授权复核」

**投标/销售物料禁止写**：
- 「一机一码」「防拷贝」「防克隆」「不可复制」——技术上不承诺（§2.1-c）
- 「硬件指纹强绑定」——容器形态下关键项是卷级盐非硬件项

**客户问「防拷贝吗」标准应答句**：
「License 采用 SM2 数字签名与多源机器指纹：防误装、防目录级拷贝、防 License 文件篡改；对整卷/整盘级克隆，技术上不做拦截——私有化交付的灾备演练与镜像分发本身依赖带卷复制，技术拦截与交付形态冲突。我们的做法是把授权合规放在审计层：激活与换绑事件全量留痕（含机器指纹），支持年度授权复核时导出比对，克隆部署会在复核中显形。」

**换绑额度商务口径（v1.4，team-lead 代 PM 裁）**：维持**统一 2 次/自然年**（License 声明可调，供应商签发时按客户合同上浮）——不引入「计划内演练/硬件更换」双额度类型（每加一层额度类型都是签发侧与交付侧的双重成本，且「演练」与「更换」在申请码层面不可区分，靠自觉的额度必然被滥用）；对灾备高频客户，走**合同侧上浮额度**（如 4 次/年）而非机制侧分型。vMotion 热迁移**不消耗额度**（数据卷不动、指纹不变、匹配不失效——只有匹配分数 < 0.70 触发换绑流程时才计数）。72h 临时授权**不做**（离线交付下临时授权文件与正式 License 无机制差异，只是又一个可拷贝的文件，防不住还多一套签发逻辑）。

## 5. 验收要点（供 QA）

1. 正常安装：物理机（或 KVM 含序列号虚机）采集 >=4 项非 absent，激活成功；
2. 单项漂移：模拟 MAC 变化（#4 失配），匹配分数仍 >= 0.70，不触发只读降级；
3. 整机克隆：克隆机关键项不达标（#1 absent + #4 veth 同前缀），激活拒绝；若为整盘克隆（盐被拷走），~~依赖席位并发检测告警兜底~~（v1.4 废止，见 §2.1-c）——改为：激活成功但**审计留痕可复核**（§6-bis 披露口径：技术不拦，年度复核时激活事件导出比对显形）；
4. 换绑流程：申请码 -> 线下签发 -> 新机器安装成功 + 旧机器 License 失效；
5. 换绑超限：第 3 次换绑申请被拒（默认上限 2 次/年），审计留痕；
6. 换回旧机器（复审打回 2 场景）：维修后换回原机器，旧指纹的 revoked 历史行不阻断重新激活（应用层只校验 active 行）；
7. **Docker 默认模式激活（P0-2）**：非特权容器、非 host 网络、docker compose 标准交付形态下，全新安装激活成功率 100%（按 §2.1-b 容器权重表判定，不依赖 dmidecode/hostname）；
8. **容器重建不漂移（P0-2）**：同一数据卷，容器 down/up 重建（hostname/MAC 均变）后指纹匹配分数不变（#5 已剔除、#6 随卷持久），不触发失效。
9. **时钟回拨（v1.4）**：激活后将系统时间回拨 90 天重启——License 判定仍按 max_seen_at（不续期），偏差 > 24h 写审计 license.clock-rollback，服务不中断；
10. **时钟前跳（v1.4）**：系统时间前跳至 expiresAt + 8 天——降级只读但提示宽限语义（宽限期 7 天内），登录/查看可用；
11. **SM2 启动断言（v1.4）**：CI 中以裁剪 OpenSSL 环境模拟（或断言代码路径单测 mock）验证 G1-G3 任一失败时进程拒绝启动；
12. **拷卷场景验收（v1.4，对齐 §2.1-c 定位）**：复制数据卷到新容器启动——激活通过（预期行为，非缺陷），审计含新激活事件（license.install 含 machine_fingerprint），导出比对可发现同指纹双活。
