# 推进计划：版本 → 需求 → 任务

> 状态：v1.0 ｜ 2026-10-25 ｜ 适用：单人 + AI 全栈（AI 承担全部编码，人只做决策与验收）｜ 单台个人电脑
> 定位：**日常唯一要看的那张表**。`backlog.csv`（788 包）降级为交付期参考，验证期不逐包维护。
> 与 `RELEASE-PLAN.md` 的关系：那边的 **v0.1~v1.0 是交付版**，已冻结、本轮不动；本文的 **V1~V6 是验证版**，两套编号互不相干。

## 1. 三层怎么分

| 层 | 单位 | 粒度 | 完成判据 | 什么时候定 | 写在哪 |
|---|---|---|---|---|---|
| **版本 V** | 一个可演示的产品增量 | 3–5 天 | 一句「能做什么」的话 | 现在一次定完 V1~V6 | 本文 §4 |
| **需求 R** | 一条端到端能力 | 0.5–1.5 天 | 演示动作（能当场做出来） | 版本开始时定 | 本文 §5 起 |
| **任务 T** | 一次会话能闭合的改动 | 0.5–2 小时 | 完成判据 + 欠账一行 | 当天定 | 本文 §5 的勾选表 |

**为什么必须补这一层**：台账里只有「需求域」（R0 工程基建 215 包、R4 导入导出 138 包），下面是 788 个 1 小时级的包——中间断档两个数量级。215 个包没法「划分任务」，1 小时的包又不值得单独称为需求。这就是失序感的来源；补上需求层，颗粒度才连续。

## 2. 一条硬规则：只细化下一层

- 现在：V1~V6 只到**需求级**；V1 细化到**任务级**。
- V1 收口那天，才把 V2 细化到任务级。**V2 的任务不要现在写**——今天写的任务，一周后大概率不作数。
- 每个版本收口日只做两件事：勾掉任务、写出下一版的任务。

## 3. 排期用 D1..Dn，不用日历

单人 + AI 的节奏不可能稳定：某天状态好推 4 个任务，某天一个依赖装不上耗 3 小时。**用日历排，落后就制造虚假压力，然后要么加班要么弃计划。**

用序号：D1、D2…… 落后就顺延，整张表不用重排。每天只问一句「今天做哪几个任务」，不问「今天该到哪天」。

## 6. V2~V6 只到需求级

**V2 能存**（H2）
- V2.1 `DataSource` 接口：`load / save / subscribe`，业务层只认它
- V2.2 IndexedDB 实现 + 编辑后节流自动保存
- V2.3 冷启动恢复：内容 + 滚动位置都在；读失败要降级到空白表而不是白屏

**V3 能同编**（H3）——本版才开始有后端，一个 Node 进程
- V3.1 单进程服务：Nest 起 HTTP + WS，SQLite 一个文件入库
- V3.2 Yjs 主路径：`seq` 定序、`snapshot@base_seq` 加载

- V3.4 断线重连：拉最新快照，不丢本地未提交改动

**V4 能进出**（H4）
- V4.1 导入：真实业务 xlsx 进来，结构/合并/数字格式不崩；公式降级为缓存值 + 角标
- V4.2 导出：产出的文件用 Excel 真能打开（这条只能用 Excel 验，不能用自己再导一次验）

**V5 能给别人**（无假设，纯包装）
- V5.1 可分享链接：URL 带文档标识，别人打开即用（**不做登录**）
- V5.2 首屏空状态 + 示例表，让人不靠旁白也能开始

**V6 验真**（H5，硬闸门）
- V6.1 找 3 个非自己、非同事的人，各用 30 分钟，全程不提示不代操作
- V6.2 记录被证伪的具体点，重定假设；**不通过就不加功能**

## 7. 每日执行协议

**开工三步（5 分钟）**

1. 看本文 §8 对应行，确认今天做哪 1 个必做 + 哪几个可选。
2. 把该任务的「内容 / 判据」贴给 AI，作为本次会话的唯一目标。
3. 先跑一次 `node scripts/verify.mjs`，确认基线是绿的（不绿就先修基线，不接新任务）。

**收工三步（10 分钟）**

1. 跑 `verify`，14/14 绿才提交；红了不提交、不叠加新任务。
2. 提交，message 里写**这一天的坑**（不是写「完成 xx」）。
3. 在 §8 勾掉任务，欠账写一行。

**四条硬规则**

1. **一天至少闭合 1 个任务**。没闭合就冻结，不并行开第二个——单人并行等于两个都做不完。
2. **一个任务超过 2 小时没闭合就拆**，不硬扛。拆出来的部分就是明天的第一个任务。
3. **验收必须真跑一次**。AI 说「应该能跑」不算，必须有一个动作你亲眼看到。
4. **欠账必须当天写**。哪天不写，第二天就会把「没做」记成「做了」。

## 9. 一台电脑的三条现实约束

1. **`verify` 就是你的 CI**。没有服务器跑流水线，一条命令跑 14 段，绿才算过。别指望「以后接 CI」，单人期它已经够用。
2. **数据库就是一个文件**（V3 起）：`var/wo.db`，进 `.gitignore`。没有 PG、没有 Docker、没有 5432 端口，不要为此装环境。
3. **别人来测（V6）需要一条隧道**：同一 WiFi 下用 `http://<本机内网IP>:端口` 就够；要远程，用 `cloudflared tunnel --url http://localhost:端口` 拿一个临时公网地址，不部署、不注册服务器。

## 10. 一个必须现在处理的风险

**这个仓库没有配置任何远程（`git remote -v` 为空），90 个提交只存在这台电脑的硬盘上。** 单人项目最大的单点故障不是技术选型，是硬盘坏掉。

选一条即可，今天做：

- 建一个**私有**仓库（GitHub / Gitee 都行），`git remote add origin ...` + `git push -u origin main`；
- 或者不联网：每天收工时 `git bundle create ../wo-backup-$(date +%m%d).bundle --all`，扔进网盘同步目录。

第一条更好——顺带解决「换电脑怎么办」。

> 2026-10-26 决定：走第一条，私有仓库由用户本人建立，AI 不动远程配置；建好后由用户执行首次推送。
