## 1. 评审结论：V3.2 要替换 V3.1 的验证期协议，不是叠加

| 能力 | V3.1 现状 | 本卡动作 |
|---|---|---|
| 帧协议 | 自有 JSON（`ready`/`message`/`ack`） | **替换**为 openapi 的二进制 lib0：`0x00 SYNC`、`0x03 LOAD`、`0x04 CONTROL`（仅 `caught-up`） |
| 持久化 | `collab_messages` 一张聊天表 | **删除**该表与 JSON 路径，新增 `yjs_updates` + `file_snapshots` |
| 服务端权威态 | 无 | 每 doc 一个 `Y.Doc`（进程内 `Map`），单实例单写者 |
| seq | 全局自增（聊天气泡） | **每文件**单调递增，`(doc_id, seq)` 主键/唯一 |
| 快照 | 无 | 显式物化 + 握手加载；`snapshot@base_seq + updates WHERE seq > base_seq` |
| 前端 | V2 单用户保存 | 新增协同模式（`?collab=<docId>`），内容通道两窗口同步；**默认单用户路径不动** |
| 鉴权 / ticket | 无 | **仍不做**；只监听回环，路径不变，偏离登记为欠账 |
| awareness / 重连 | 无 | **不做**（V3.3 / V3.4） |

明确不做：ticket/登录、权限与席位、awareness、PING/PONG、断线重连、结构通道（插行/删列/合并）、服务端无头 Univer 重算、TypeORM/迁移、PG/Redis/Docker、openapi 与 `@wo/shared` 错误码修改、V2 本地文档迁入协同。

**V3.1 探针的去向**：`scripts/probe-server.mjs` 的 11 条判据绑定 JSON 协议与 `collab_messages`，V3.2.1 落地时一并退役；同提交新增 `scripts/probe-collab.mjs`。V3.1 的收口证据保留在 `evidence/v3-closeout-server-log.txt`，不回头改历史。

## 2. 拟拍决策（开工前确认）

| 未定点 | 本卡选择 | 为什么 / 否决了什么 |
|---|---|---|
| Yjs 版本 | `yjs 13.6.33` + `y-protocols 1.0.7` + `lib0 0.2.119`，全部精确版本 | 13.6 系列已在 Phase 2 锁定；2026-10-27 registry 查询的 13.6 最新 patch 是 13.6.33。`y-websocket` 不引入——服务端要自己控 seq 与持久化时序，客户端直接吃 `y-protocols/sync` |
| 快照字节 | **Yjs state update**：`Y.encodeStateAsUpdate(ydoc)` → gzip(6) → Base64/BLOB | `SYNC_STEP1/2` 的差量同步必须基于同一份 Y.Doc；若快照是 Univer workbook JSON，客户端无法从它恢复 Y.Doc 的 CRDT 历史。`schema.md` 与 openapi 的「无头 Univer 物化」改为交付轨描述，本卡开工先修文档 |
| seq 语义 | **每文件** `max(seq)+1`，单写者；doc 内严格递增、允许不连续 | 与 `schema.md §3.5`、D1-06 一致。全局 seq 会让「每文件 max(seq)」失去意义；号段预分配（≤1000/段）本卡不做，登记欠账 |
| 落库时序 | write-through：先提交 `yjs_updates`，再广播；单条提交，不做 group-commit | 攒批会把 RPO 从 0 变成「≤1s/≤50 条」；V3.2 的判据要强杀后可重建，先取最简且最强的时序。group-commit 与号段预分配归交付轨 |
| 物化触发 | **只做显式 POST** `/api/v1/files/{id}/snapshot`；30min/500 条两个节流条件不做 | 判据需要「可控地制造 snapshot@base_seq」，显式触发是唯一确定性的入口；自动物化是策略层，V3 不验它。GET 同路径返回最新快照 |
| 快照版本 | 每文件 `version = max(version)+1`，`base_seq = 物化时刻 max(seq)`，同一事务 | D1-06/openapi 的固定语义；V3.2 用 SQLite 单事务实现，不引入 TypeORM |
| LOAD 与增量 | 握手发 `LOAD{version, baseSeq, snapshot}` → `SYNC_STEP1` → 客户端 `SYNC_STEP2` → 按 seq 升序回放 `seq > baseSeq` → `CONTROL caught-up` | openapi handshake 的固定顺序。`caught-up` 是就绪点：收到前客户端不出站；本卡只做单次连接，不做重连 |
| 内容通道 | `commandService.onCommandExecuted` 拦截 → `Y.Map<地址, {v,f}>` 幂等绝对赋值 → 远端 `{onlyLocal:true, fromCollab:true}` 回放 | ADR-001 Decision 1。结构通道按 Decision 2 需要服务端定序 oplog，本卡不做（见 §6 欠账 2） |
| 初始内容 | 协同模式用 V1 的确定性 3×3 演示数据播种；两端首次连接若服务端 Y.Doc 为空，各自写入同一组绝对赋值 | 绝对赋值幂等，两端同时播种也不会发散。V2 本地文档如何进入协同是独立问题（V3.1 欠账 11），本卡不解决，避免「两台机器拿不同本地库合并」这种不可解释的状态 |
| 前端入口 | `?collab=<docId>` 才走协同；不带参数时 V2 单用户路径**一行不改** | V3.2 是验证版，不能把 V2 已收口的持久化改坏。协同模式关闭 IndexedDB 自动保存（服务端权威），避免双写 |
| 鉴权 | 不做；仍只监听 `127.0.0.1`；`ticket` 查询参数接受但不校验 | V5.1 前没有登录。伪鉴权比无鉴权危险；契约偏离继续挂账 |
| 服务端无头 Univer | **不做**；服务端只存 Yjs 原始输入，不重算、不产 Univer 快照 | V3.2 的判据是「两窗口内容收敛」，不是「服务端权威重算」。引入无头 Univer 会同时带来公式引擎线程、LRU 与快照口径三块未决问题，超出本卡 |

## 4. 实现方案

### 4.1 依赖与入口

`apps/server/package.json` / `apps/web/package.json`：

```json
"dependencies": {
  "yjs": "13.6.33",
  "y-protocols": "1.0.7",
  "lib0": "0.2.119"
}
```

- 服务端与前端都装（两端都要构造/同步 Y.Doc；`y-protocols` 的 sync 消息两端共用）。
- 只加这三个；`y-websocket` 不装——它自带的重连与协议封装会绕过本卡的 seq/持久化控制。
- 改完 `corepack pnpm install`，由 lockfile 与包内 `node_modules` 同时到位；不手改 lockfile。

### 4.2 服务端存储：替换 `WoDb` 的两张表

`apps/server/src/db/wo-db.ts` 保留「单文件、仓库根解析、WAL、STRICT」这些已验证的选择，删掉 `collab_messages`，建：

```sql
CREATE TABLE IF NOT EXISTS yjs_updates (
  doc_id     TEXT    NOT NULL,
  seq        INTEGER NOT NULL,
  update_blob BLOB   NOT NULL,
  origin     TEXT    NOT NULL,
  created_by TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (doc_id, seq)
) STRICT;

CREATE TABLE IF NOT EXISTS file_snapshots (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id     TEXT    NOT NULL,
  version    INTEGER NOT NULL,
  base_seq   INTEGER NOT NULL,
  snapshot   BLOB    NOT NULL,
  created_by TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  UNIQUE (doc_id, version)
) STRICT;
```

接口（全部同步）：

| 方法 | 语义 |
|---|---|
| `appendUpdate(docId, update: Uint8Array, origin, createdBy)` | 事务内 `seq = max+1` → INSERT → COMMIT，返回 seq；`update_blob` 按原字节存 |
| `updatesSince(docId, baseSeq)` | `WHERE seq > ? ORDER BY seq ASC`，返回 `{seq, update: Uint8Array}[]` |
| `latestSnapshot(docId)` | 最大 `version` 行，返回 `{version, baseSeq, snapshot: Uint8Array}` 或 null |
| `materialize(docId, state: Uint8Array, createdBy)` | 事务内 `baseSeq = max(seq)`、`version = max(version)+1`、INSERT；返回 `{version, baseSeq}` |
| `close()` | 幂等关闭 |

- `BLOB` 用 `Uint8Array` 绑定/读回；`node:sqlite` 对 `Uint8Array` 原生支持，读回可能是 `Uint8Array`，不转字符串。
- 删除 `collab_messages` 前先确认 `var/wo.db` 是验证库；不写迁移脚本，旧库由使用者自行删除（欠账）。

### 4.3 服务端 Yjs 核心：`collab-core.service.ts`

- `Map<docId, { ydoc: Y.Doc, clients: Set<WebSocket>, loading: boolean }>`；单实例单写者。
- 首连：读 `latestSnapshot` → 构造空 `Y.Doc` → `Y.applyUpdate(doc, snapshot)`（无快照则空）→ 发 `LOAD` → 发 `SYNC_STEP1`（本 doc 的 state vector）→ 客户端回 `SYNC_STEP2` → 服务端 `Y.applyUpdate` 并回放 `updatesSince(baseSeq)` → 发 `CONTROL caught-up`。
- 客户端 `UPDATE`：`Y.applyUpdate` → **先** `appendUpdate` 提交 → 再广播给同房其它连接（不含发送者回声）；写失败关 1011，不广播。
- `SYNC_STEP1/2` 用 `y-protocols/sync` 的 `readSyncMessage/writeSyncMessage`，帧头 `0x00`。
- `doc-rebuild`、awareness、PING、ROLE_UPGRADE 一律不实现；收到 `0x01/0x02/0x05` 直接 1008，收到未知帧类型 1008。
- 非法 lib0 编码/截断 → 1003；`maxPayload` 64KB 不变（超限由 `ws` 回 1009）。
- 连接断开只出房，不销毁 `Y.Doc`；本卡没有 LRU/驱逐，进程退出即释放。

### 4.4 快照端点：`apps/server/src/modules/files/files.controller.ts`

- `POST /api/v1/files/:id/snapshot`：取该 doc 的内存 `Y.Doc`（未加载则按库重建）→ `Y.encodeStateAsUpdate` → `db.materialize` → 返回 `{version, baseSeq}`。
- `GET /api/v1/files/:id/snapshot`：返回 `{version, baseSeq, snapshot: gzip+Base64}`；无快照 404，错误体走既有 `AllExceptionsFilter`。
- 归属：`FilesModule` imports `CollabModule`，`CollabModule` exports `CollabCoreService`；模块图从 10 模块 / 0 依赖变为 10 模块 / 1 依赖，仍零环（`files → collab`，反向不存在）。
- 无鉴权、无文件存在性校验（没有 files 表）；`id` 走与 WS 相同的 `[A-Za-z0-9_-]{1,64}` 校验。这些偏离登记欠账。

### 4.5 前端协同模式：`apps/web/src/collab/*`

- 入口：`?collab=<docId>` 时挂协同；不带参数时沿用 V2 的 `SheetHost`/`attach-data-source`/`autosave`，一行不改。
- 连接：`new WebSocket('/ws/collab/' + docId)`；`binaryType = 'arraybuffer'`；按帧头分发 `0x00/0x03/0x04`。
- 加载：收 `LOAD` → `Y.applyUpdate(ydoc, gunzip(Base64))` → 回 `SYNC_STEP1` → 收 `caught-up` 前**不出站**。
- 出站：`commandService.onCommandExecuted` 拦截 → 只处理内容类 mutation → 写 `Y.Map`（`{v, f}` 绝对赋值）→ 编码 `Y.encodeStateAsUpdate(ydoc, stateVector?)` 或 `Y.encodeStateVector` 差量 → 发 `0x00 UPDATE`。
- 入站：收到远端 update → `Y.applyUpdate(ydoc, update, 'remote')` → 把变化映射为 `setValue/setFormula` 命令，带 `{onlyLocal: true, fromCollab: true}` 执行；`fromCollab` 为真时不再出站，防回声环。
- 初始播种：`caught-up` 后若 `Y.Map` 为空，写入 V1 的 3×3（A1=1、A2=2、A3=`=SUM(A1:A2)`）；两端写同一组绝对赋值，幂等。
- 协同模式**不接 V2 的 IndexedDB 自动保存**；本地视口恢复也不做（避免把单用户状态混入协同判据）。

### 4.6 探针

**A. `scripts/probe-collab.mjs`（服务端，Node 22 + `yjs`）**

两个进程内 Yjs 客户端直连 `ws://127.0.0.1:3100/ws/collab/<doc>`，不依赖浏览器。判据：

| 编号 | 动作 | 断言 |
|---|---|---|
| C0 | health | JSON 且 body 精确 `{status:'ok'}` |
| C1 | A/B 首连空 doc | 都收到 LOAD（version=0/baseSeq=0）+ caught-up；两端 doc 为空 |
| C2 | A 写 A1=5 | B 收到 update 后 A1=5；A 不回显 |
| C3 | B 写 A2=7 | A 收到；两端 state vector 一致 |
| C4 | 旁路直读 `yjs_updates` | doc 内 seq 严格递增；`update_blob` 可被独立 `Y.applyUpdate` 还原出 A1/A2 |
| C5 | `POST /files/:id/snapshot` | 返回 `{version:1, baseSeq:2}`；`GET` 返回同 baseSeq 且快照可解出 A1/A2 |
| C6 | 再写 A3 | seq=3；重连的新客户端收到 `snapshot@2 + update(3)`，状态与 A/B 一致 |
| C7 | doc-b 隔离 | doc-b 的 seq 从 1 开始；doc-a 的消息不进 doc-b |
| C8 | 强杀重启 | 重开库，`yjs_updates` 行数与 seq 完整；新客户端按 `snapshot@base_seq + seq>base_seq` 重建出 A1/A2/A3 |

**B. `scripts/probe-collab-web.mjs`（浏览器，两个 page target）**

复用 `probe-web.mjs` 的 CDP 起法与 `window.__woSheet` 句柄，但**开两个 page target**（两个标签页同源）。判据：

| 编号 | 动作 | 断言 |
|---|---|---|
| W1 | 两页都开 `?collab=e2e-a` | 都显示 A1=1、A3=3（3×3 播种生效） |
| W2 | 页 1 `setValueByA1('A1', 5)` | 页 2 的 A3 在 3 秒内变 7，且页 2 **未刷新** |
| W3 | 页 2 `setValueByA1('A1', 9)` | 页 1 的 A3 变 11（反向） |
| W4 | 页 3 迟到进房 | 直接看到 A1=9、A3=11 |
| W5 | 两页各改一次后静置 2 秒 | 无控制台 error、无 `fromCollab` 回声环（命令执行次数有上界） |

### 4.7 判据为什么不会恒真

| 判据 | 可能被什么假绿骗过 | 防法 |
|---|---|---|
| C2/C3 | 客户端只在本地改，广播从未发生 | 对端必须读到新值；反向再发一次；两端 state vector 比对 |
| C4 | 「广播对了」被当成「入库了」 | 绕过应用代码，用独立 `Y.Doc` 应用库里的 `update_blob` |
| C5 | 快照接口返回 201，但 baseSeq 与库里不一致 | 用独立连接读 `file_snapshots`，断言 `base_seq = max(seq)` 且字节可解出相同状态 |
| C6 | 重连拿到的是内存态，不是「快照+增量」 | 杀进程后重开库，且新连接只允许走 LOAD + 增量 |
| C7 | 没消息也能「隔离」 | doc-b 必须有自己从 1 开始的 seq，doc-a 继续递增 |
| W2 | 页 2 其实刷新过 | 在页 2 写一个「刷新即丢」的标记（如 `window.__marker = random`），W2 后检查标记仍在 |
| W3 | 只有单向上行 | 反向再发；两端命令次数与最终值都要对 |
| W5 | 回声环被 2 秒窗口错过 | 统计 `onCommandExecuted` 次数，设明确上界（如 ≤ 20）；同时断言无 error |

### 4.8 反向对照（至少三条）

| 编号 | 一行破坏 | 预期变红 | 预期仍绿 | 证明什么 |
|---|---|---|---|---|
| R1 | `appendUpdate` 只广播不 INSERT | C4 C5 C6 C8 | C0 C1 C2 C3 C7 | 持久化判据真的在读库 |
| R2 | LOAD 不应用快照（永远发空 doc） | C6 C8 | C1 C2 C3 C4 C5 C7 | 重连/重启真的走了 snapshot@base_seq |
| R3 | 服务端广播循环跳过 | C2 C3 C6 | C4 C5 C7 C8 | 实时判据真的在测扇出 |
| R4 | 前端入站不设 `fromCollab` 抑制 | W5 | W1 W2 W3 W4 | 回声环判据能抓住「看起来同步了但无限回写」 |

### 5.2 已知风险（按杀伤力排序）

1. **Univer 1.2.0 的 mutation 拦截形态与 ADR 假设不一致**——开工第一小时先实测；不一致就停在闸门 2，不硬写。
2. **`onCommandExecuted` 的回放会再次触发自身**——`fromCollab` 标记必须在执行选项里，且拦截器要在最前面；W5 就是为它设的。
3. **Y.Doc 初始状态不一致**——两端各自播种绝对赋值可收敛，但只要有一端用「相对操作」或带时间戳的值就会发散；本卡只允许 `{v,f}` 绝对赋值。
4. **`node:sqlite` 的 BLOB 绑定**——`Uint8Array` 与 `Buffer` 都要实测；写入后读回字节逐字比对，不靠 `JSON.stringify`。
5. **Windows 强杀**——与 V3.1 相同，`child.kill()` 不保证 JS 信号；C8 用强杀后重开库，不验优雅关闭。
6. **两个 page target 同源同库**——localStorage/IndexedDB 共享；协同模式已关闭 IndexedDB 自动保存，但视口等状态仍可能互相影响，探针不依赖它们。

## 6. 欠账

1. **鉴权与 ticket**：无 ticket 校验、无权限、无席位、无 4410/4411/4412；V5.1 前不得对外宣称符合 openapi WS 契约。
2. **结构通道未做**：插行/删列/合并/排序等非幂等操作没有服务端定序 oplog，两窗口做结构操作会发散。V3.2 只验内容通道；**V3.3 卡必须先排这块，否则 V3 不能说「不打架」**。
3. **无 awareness / PING / 重连 / 断点续传**：V3.3 / V3.4。
4. **服务端不重算、不产 Univer 快照**：快照是 Yjs state；「无头 Univer 权威重算」归交付轨。schema.md/openapi 的描述待修。
5. **seq 不做号段预分配、不做 group-commit**：每写一条一次事务，RPO=0 但吞吐低；交付轨按 ADR-001 v1.3 调整。
6. **无自动物化**：30min/500 条不实现，只有显式 POST；重启后靠 `yjs_updates` 全量回放，长日志会慢。
7. **无快照/增量保留与清理**：`file_snapshots` 与 `yjs_updates` 只增不减（OPEN 未决，禁止提前实现删除）。
8. **无 LRU/内存水位**：`Y.Doc` 连接归零也不释放，活跃 doc 无上限；4412 未实现。
9. **`created_by` 是匿名占位**：无登录，写 `anonymous`；审计留痕不成立。
10. **V2 本地文档不进入协同**：协同模式用演示数据播种，用户在 V2 存的内容不会出现在协同 doc；反向也不回写。
11. **删除 `collab_messages` 无迁移**：验证库 `var/wo.db` 由使用者自行删除；不写迁移脚本。
12. **浏览器探针依赖两 page target 与 `?collab=` 入口**：多标签页共享 IndexedDB/localStorage 的干扰未系统验证。
