## 1. 评审结论：V3.3 的第一项不是 awareness，是结构通道

| 能力 | V3.2 现状 | 本卡动作 |
|---|---|---|
| 单元格内容 | `Y.Map<A1,{v,f}>` 绝对赋值；两窗口已收敛 | **不改语义**，只补结构操作后的坐标/公式写回 |
| 结构操作 | 只过滤 `sheet.mutation.set-range-values`；插行/删列在另一端**完全不可见**，且之后的内容坐标会错位 | 新增结构通道：服务端定序、客户端按序回放、发起端写回 |
| 公式引用 | 引擎在结构操作时由 `FormulaRefRangeService` 改写 | 必须保证两端改写到同一结果；以发起端引擎回读为权威 |
| 快照/加载 | `snapshot@base_seq + seq > base_seq` | 快照新增 `meta`（行列数）；**不重放历史结构 op** |
| awareness | 未做 | `0x01 AWARENESS` + `y-protocols/awareness`，不落库 |
| 断线重连 | 未做 | **仍不做**（V3.4） |
| 鉴权 / ticket | 未做 | **仍不做**（V5.1） |

明确不做：`move-range`、合并/取消合并、排序/自定义排序、多工作表结构操作、断线重连、PING/PONG、ticket/登录、服务端无头 Univer 重算、TypeORM/迁移、自动物化、像素级浮标光标。

> **范围裁决**：本卡只把「行列插入/删除」这一族坐标平移做成闭环。`move-range` 与合并仍会发散，**必须在 V3.4 或更早单独排掉**；在此之前，V3 不能说「任何结构操作都不打架」。排序若只产生单元格绝对赋值，可被 V3.2 内容通道覆盖，但要用探针证明，不能默认。

## 2. 拟拍决策（开工前确认）

| 未定点 | 本卡选择 | 为什么 / 否决了什么 |
|---|---|---|
| 结构 op 的本地执行 | **先否决，后按服务端回执执行**：`interceptBeforeCommand` 返回 `false`，发提案；收到 `struct-applied` 再 `syncExecuteCommand` 回放 | 所有端执行同一序列，公式引用改写与坐标迁移必然一致；不需要本地回滚/rebase。代价是结构操作多一个 RTT（本机 ms 级，结构操作低频）。否决「本地先执行、服务端定序后再修」：Univer 1.2.0 没有可靠的单元格级 rebase，回滚只能整簿重建 |
| 定序者 | **服务端单写者按到达顺序**分配 `opSeq`；客户端不写结构 op 序号 | ADR-001 Decision 2 与 openapi `server-responsibilities` 已定；单实例单写者与 V3.2 的 seq 语义同构 |
| 帧 | 新增应用层 `0x06 STRUCT`（C→S 提案）；`0x04 CONTROL` 新增子类型 `struct-applied` / `struct-rejected` | 不复用 `0x00 SYNC UPDATE`：Yjs update 是合并语义，客户端若把它当有序日志，Yjs 会按 client id 排，和到达序不一致。`0x05` 已给 ROLE_UPGRADE |
| 结构 op 形状 | `{opId, clientId, command, params}`；`command` 只收 `sheet.command.insert-row/remove-row/insert-col/remove-col` 及其官方 range 变体；`params` 原样转发但服务端白名单校验 | 只同步用户入口命令，不自己发明结构模型；服务端校验 `unitId/subUnitId/range`，拒绝负数、越界、`count=0`、未知命令 |
| 持久化 | 新增 `structure_ops(doc_id, op_seq, op_id, client_id, command, params_json, created_at)`；`(doc_id,op_seq)` 主键、`(doc_id,op_id)` 唯一；与同 doc 的 `meta` 更新同一事务 | 定序与去重可跨重启；`opId` 重发幂等。**加载不重放**这张表——内容与几何都在 Y.Doc/快照里，重放会把已迁移的内容再平移一次 |
| 几何元数据 | 新增 Y.Map `meta`：`rowCount`、`colCount`（后续可扩 `merges`）；**只由服务端写** | 迟到的客户端只需 `snapshot + meta` 就能把网格恢复成正确大小，不需要历史结构 op |
| 内容坐标迁移 | 服务端**不解析公式**；发起端回放后把引擎回读的整张已用区域写回 `Y.Map`，服务端广播该内容 update | 公式引用改写由 Univer 引擎负责（`FormulaRefRangeService`），服务端不装无头 Univer。回读以发起端引擎为权威，其他端先执行同一命令、再被写回覆盖，幂等 |
| 写回范围 | 发起端回读**整张已用区域**（含公式格只发 `{f}`），并用一次事务删除 `Y.Map` 中已不存在的键 | 结构操作会影响「任何引用被移动区域的公式」，无法只靠坐标附近判断；V3.3 先取正确性，规模债务登记 §6 |
| 结构窗口 | 服务端对每个 doc 维护 `structInFlight`：窗口内**暂停新连接 LOAD**（或延迟到写回落库后发 `caught-up`），已有连接照常收帧 | 避免新连接在「结构已应用、内容写回未到」的中间态读到旧内容；结构操作低频，暂停窗口可接受 |
| awareness | `0x01` + `y-protocols/awareness`；服务端中继、**不落库、不进快照**；断开发 `removed` | openapi 已定义 0x01；awareness 是易失状态，落库会让「在线」在重启后变成幽灵 |
| 在线身份 | 每个标签页随机 `clientId` + 显示名（`用户-<4位>`）；不接登录 | 无鉴权；同一人多标签页算多个在线，V3.3 不引入席位语义 |
| 光标呈现 | **在线名单 + 当前选中格地址**（presence bar）；像素级浮标光标不做 | Univer OSS 无协同光标插件；自绘浮标要处理滚动/缩放/合并区，超出本卡验证范围。先让「谁在看哪一格」可判 |

## 4. 实现方案

### 4.1 帧与结构 op（服务端契约）

```text
0x06 STRUCT（C -> S，应用层）:
  writeVarString(JSON.stringify({
    opId: string,          // 客户端生成，重发幂等
    clientId: string,      // 标签页级随机 id
    command: string,       // 白名单命令 id
    params: object         // unitId/subUnitId/range 等原样参数
  }))

0x04 CONTROL（S -> C，应用层子类型）:
  { type: 'struct-applied', opSeq: number, opId: string, clientId: string, command: string, params: object }
  { type: 'struct-rejected', opId: string, code: 'invalid' | 'busy' | 'too-large', message: string }
```

- 服务端按到达顺序处理；同一 doc 的 `opSeq = max(opSeq)+1`，`(doc_id, op_id)` 唯一。重复 `opId` 不重新分配，直接回放上次的 `struct-applied`。
- 参数校验（边界，不是业务）：`unitId` 必须是当前 doc 的 `unitId`；`subUnitId` 必须是当前表；`range` 的行列必须是非负整数且不超当前行列数；`count` 必须 1～1000；拒绝 `move-range`、合并、排序与未知命令。
- 收到非法结构帧按 1008 关闭（方向/能力不符），lib0 截断或 JSON 解析失败按 1003；与 V3.2 的 C9 守门同口径。
- 新增表：

```sql
CREATE TABLE IF NOT EXISTS structure_ops (
  doc_id      TEXT    NOT NULL,
  op_seq      INTEGER NOT NULL,
  op_id       TEXT    NOT NULL,
  client_id   TEXT    NOT NULL,
  command     TEXT    NOT NULL,
  params_json TEXT    NOT NULL,
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (doc_id, op_seq),
  UNIQUE (doc_id, op_id)
) STRICT;
```

### 4.2 服务端：`CollabCoreService` / `WoDb`

- `WoDb` 增加 `appendStructureWithUpdate(docId, opId, clientId, command, paramsJson, metaUpdate, createdBy)`：**一个 `BEGIN IMMEDIATE` 事务**内分配 `opSeq`、`INSERT structure_ops`、分配内容 `seq`、`INSERT yjs_updates`（`metaUpdate` 在进入事务前由 `Y.Doc.transact` 生成）。提交后再广播 `struct-applied`。禁止拆成「先写 op 表、后写 meta」两步——那会在重启窗口留下「op 已定序、几何未变」的半状态，且违反 V3.2 的 write-through 口径。
- `meta` Y.Map 只由服务端写：`rowCount`、`colCount`；每次结构 op 在 `Y.Doc.transact` 内更新。客户端的 `meta` 观察者只读，不写出站。
- 处理顺序（每个 doc 串行）：
  1. 收到 `0x06` → 校验 → `opSeq` 分配 → 持久化（含 `meta`）→ 广播 `struct-applied` 给**所有**连接（含发起端）。
  2. 发起端回放命令后，回读已用区域，发一次 `0x00 UPDATE`（内容写回）。
  3. 服务端按 V3.2 的 write-through 落库并广播该 update。
  4. `structInFlight` 在「收到发起端写回」或超时（如 5s）后清除；窗口内新连接先不发 `caught-up`，等写回落库后再走加载协议。
- 断线/超时：发起端在窗口内断开 → 服务端清除 `structInFlight`，广播 `struct-rejected`（或 `struct-aborted`）让其它端把该 op 视为失败；**不**回滚已分配的 `opSeq`（seq 允许不连续）。该 doc 的下一次结构 op 重新定序。此路径必须有探针，否则「卡在窗口」会成为挂死。

### 4.3 客户端：`apps/web/src/collab/*` 与 `mount-sheet.ts`

- **拦截**：`ensureStructureWiring()` 懒接线（只有协同模式调用）。从 `univer.__getInjector()` 取 `SheetInterceptorService`，`interceptBeforeCommand` 注册 `performCheck`：
  - `applyingRemote === true` → 放行；
  - 命令不在白名单 → 放行；
  - `status !== 'ready'` → 拒绝并提示「协同未就绪」；
  - 否则**拒绝**本地执行，生成 `opId`，把 `{command, params}` 交给 `CollabClient.sendStructure()`，进入 `structPending` 状态。命令返回 `false`，画面不变——这是有意的：等回执，不做本地乐观执行。
- **回放**：收到 `struct-applied` 后，`applyingRemote = true`，`univerAPI.syncExecuteCommand(command, params, { onlyLocal: true, fromCollab: true })`，`finally` 复位。回放期间派生的所有内部命令（如 `insert-row-by-range`）由同一个守卫放行，不能再生成第二个提案。
- **写回**：只有发起端（`clientId` 命中本地）执行。回放后新增 `handle.readUsedCells()`：从当前工作簿的 `cellData` 枚举已用区域，公式格只取 `f`、常量格取 `{v, f:''}`，得到 `CellPatch[]`；`CollabClient.replaceAll(cells)` 在**一个** `ydoc.transact(..., LOCAL_ORIGIN)` 内 set 全部键并 delete 已不存在的键，产生一条 update 发往服务端。写回后清 `structPending`。
- **拒绝/超时**：收到 `struct-rejected` 或 5s 未收到 `struct-applied` → 清 `structPending`，在页面状态栏提示「结构操作未同步」；不重试、不本地补执行（重试会制造重复 `opId`，由 §3 的幂等路径处理；V3.3 先不自动重试）。
- **结构窗口内的内容编辑**：服务端在 `structInFlight` 期间把其它连接的内容 UPDATE 缓冲在内存（不落库、不广播）；发起端写回落库后，先广播写回，再按到达顺序 flush 缓冲。这样「结构 op → 写回」是一个对客户端可见的原子段，缓冲中的内容编辑在写回之后生效（LWW），不会被写回吞掉。缓冲上限与超时见 §6 欠账。
- **undo/redo**：结构命令的 undo 也是结构命令，同样被拦截并作为新提案；回放是否进入本地 undo 栈由闸门 2 决定。若回放会入栈，回放时用一个「不记录 undo」的执行选项或临时关闭 undo 记录，禁止出现「远端操作出现在我的撤销历史里」。

### 4.4 几何元数据与加载

- `LOAD` 载荷形状**不变**（`{version, baseSeq, snapshot}`）；`meta` 是 Y.Doc 里的 `Y.Map`，随快照/增量自然传输，不新增 LOAD 字段。
- 客户端在 `caught-up` 后、整表内容核对之前，读 `meta.rowCount/colCount`，用 `sheet.command.set-worksheet-row-count` / `set-worksheet-column-count` 把引擎恢复到服务端几何；执行时同样置 `applyingRemote`，防止内容通道出站。
- **不重放 `structure_ops`**：内容已经是最终坐标，重放历史 op 会二次平移。`structure_ops` 只服务于定序、幂等与审计；重启后从 Y.Doc/快照恢复内容与几何。
- 服务端 `materialize()` 无需改代码：`Y.encodeStateAsUpdate` 自动包含 `meta`；`base_seq` 仍然是物化时刻 `max(seq)`。

### 4.5 awareness（在线名单 + 选中格）

- 服务端：每 doc 一个 `Awareness`（`y-protocols/awareness`）。收到 `0x01` → `applyAwarenessUpdate(awareness, update, ws)` → 向其它连接转发同一编码；连接断开时 `removeAwarenessStates(awareness, [clientId], 'disconnect')` 并广播。**不写 yjs_updates、不进快照**。
- 客户端：`Awareness(ydoc)`，本地状态 `{ user: { id, name, color }, selection: { sheetId, startRow, startColumn, endRow, endColumn } }`。`univerAPI.Event.SelectionChanged`（参数 `selections: IRange[]`）触发本地状态更新，50ms 节流后发 `0x01`；收到远端 awareness 后渲染 presence bar。
- 呈现：页头 `app-meta` 位显示「在线 N 人」+ 每人色点和「名字 · A1」；选中格用地址文本表达，不做像素级浮标光标（§2）。关闭页面后服务端移除该状态并在 5s 内推给其它端。
- awareness 帧大小上限沿用 `maxPayload` 64KB；非法 awareness 编码 → 1003，不关整条内容通道以外的连接（与 SYNC 解析失败同口径）。

**C. 判据为什么不会恒真**

- 结构断言必须读**引擎**的整表矩阵（`__woSheet.getSnapshot()` 或逐格 `getValueByA1`），不读我们的 `meta`/Y.Map 镜像；
- 并发用例必须让 A/B 的提案在服务端窗口内真正重叠（用探针在同一 tick 发出，并在服务端日志确认两个 `opSeq`），否则「串行」是假绿；
- 「未刷新」用随机 marker；「无幽灵格」用全表快照逐格比对，不能只看几个抽样点；
- 「公式正确」同时断言公式文本引用与计算值，避免只看到缓存值。

## 5. 判据与风险

### 5.1 正向判据

- 服务端 C0~C15 全绿（C0~C9 不回归，新增 C10~C15）；
- 浏览器 W0~W10 全绿（W0~W5 不回归，新增 W6~W10）；
- `node scripts/verify.mjs` 14/14；
- 证据落 `docs/phase3/evidence/v3.3-server-log.txt`、`v3.3-web-log.txt`、结构/awareness 截图。

### 5.2 已知风险（按杀伤力排序）

1. **否决点不在命令层**：若 `interceptBeforeCommand` 未被某个结构命令 handler 调用，或返回 `false` 只跳过附属 mutation 而主 mutation 仍执行，方案不成立。闸门 1 必须先证明；不成立就退回「服务端定序 + 发起端整簿重建」，并重新评估是否值得。
2. **内部命令重复提案**：`insert-row` 内部 `syncExecuteCommand('sheet.command.insert-row-by-range')` 会被拦截器再看到一次。必须用 `applyingRemote` 与命令栈/trigger 识别外层，否则一次插行变成两次。
3. **公式改写不等价**：远端回放与本地执行的公式引用改写若有差异，写回会把发起端的文本覆盖过去；若发起端写回不完整，迟到客户端会拿到旧引用。闸门 2 与 R7 是这条的防线。
4. **写回吞并发编辑**：结构窗口缓冲只能覆盖「窗口内」；窗口外到达的内容编辑仍可能与写回竞争。V3.3 用 LWW 接受，探针必须在窗口内制造并发并证明不丢。
5. **大表写回成本**：整张已用区域写回是 O(已用格数)，200×30 的演示表可接受，万行表会明显卡顿。V3.3 只验正确性，规模优化登记 §6。
6. **`meta` 与引擎行列数不一致**：Univer 的 `set-worksheet-row-count` 若不能缩小到已有内容之外，删除行后的加载会截断/多出空行；闸门 3 必须覆盖「增」和「减」两个方向。
7. **awareness 生命周期**：y-protocols 的 timeout 与浏览器后台标签页节流可能让「在线」延迟消失；W9 的 5s 上限要留余量，不能用 1s 卡死。
8. **服务端结构窗口挂死**：发起端断线或写回帧丢失时必须有超时与 `struct-rejected` 路径；否则该 doc 后续结构操作与 LOAD 全部阻塞。

## 6. 欠账

1. **`move-range`、合并/取消合并、排序未覆盖**：仍会发散；必须在 V3.4 或 V3.3 收口后的独立任务里闭环，V3 之前不得宣称「所有结构操作都不打架」。
2. **没有服务端无头 Univer**：公式引用改写以发起端引擎为权威；恶意/有 bug 的客户端可以写出与引擎不一致的公式文本。V5.1 有鉴权后仍需服务端校验。
3. **整表写回**：O(已用格数)，无增量 diff、无范围裁剪；大文档会卡。
4. **结构窗口缓冲无持久化**：窗口内其它端的内容编辑只在内存，发起端断线/服务重启会丢；V3.4 重连时再定策略。
5. **`structure_ops` 只增不减**：无清理/归档；加载不重放，但表会随结构操作增长。
6. **无多工作表/工作簿级结构操作**：只处理当前 `subUnitId`；新增/删除/重命名工作表不在本卡。
7. **无 undo 协同语义**：远端结构回放是否入 undo 栈由闸门 2 决定；「撤销别人的操作」不支持（业界默认）。
8. **awareness 无持久化、无重连、无 PING**：在线状态是易失的；标签页级身份，不接登录/席位。
9. **像素级光标浮标未做**：只有在线名单 + 选中格地址。
10. **鉴权/ticket 仍缺席**：同 V3.2 欠账 1。
11. **服务端结构 op 校验是白名单级**：不校验工作表是否存在、不校验用户权限（没有权限模型）。
12. **`structure_ops` 与 `yjs_updates` 的跨表原子性**：取决于 §4.2 的实现选择；若为两步写，重启窗口内可能出现 op 已记但 meta 未记，必须在卡里写清并接受或合并事务。
