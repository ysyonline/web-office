### 4.2 数据库层：`apps/server/src/db/wo-db.ts`

一个文件、一个类、一张表。**不放 `*.module.ts`**，作为 provider 注册在 `CollabModule`，避免动模块图。

```ts
@Injectable()
export class WoDb implements OnApplicationShutdown {
  private readonly db: DatabaseSync;
  private closed = false;

  constructor() {
    const raw = process.env.WO_DB_URL?.trim();
    if (!raw) throw new Error('[WoDb] WO_DB_URL 为空');
    if (/^[a-z][a-z0-9+.-]*:\/\//i.test(raw)) {
      throw new Error('[WoDb] V3.1 只支持 SQLite 文件路径，不支持 URL');
    }
    const file = isAbsolute(raw) ? raw : resolve(findRepoRoot(process.cwd()), raw);
    mkdirSync(dirname(file), { recursive: true });
    this.db = new DatabaseSync(file);
    this.db.exec('PRAGMA journal_mode = WAL');
    this.db.exec('PRAGMA synchronous = NORMAL');
    this.db.exec('PRAGMA busy_timeout = 5000');
    this.db.exec(`
      CREATE TABLE IF NOT EXISTS collab_messages (
        seq        INTEGER PRIMARY KEY AUTOINCREMENT,
        doc_id     TEXT NOT NULL,
        text       TEXT NOT NULL,
        created_at INTEGER NOT NULL
      ) STRICT;
      CREATE INDEX IF NOT EXISTS idx_collab_messages_doc_seq
        ON collab_messages(doc_id, seq);
    `);
  }
}
```

接口（全部同步，`node:sqlite` 就是同步 API）：

| 方法 | 语义 |
|---|---|
| `append(docId, text)` | 插入一行，返回 `{ seq, at }`；`lastInsertRowid` 是 `number \| bigint`，转 `Number` 并断言安全整数 |
| `history(docId, limit = 100)` | 最近 N 条，**按 seq 升序**返回（先 `ORDER BY seq DESC LIMIT ?` 再外层升序） |
| `close()` | 幂等关闭；`OnApplicationShutdown` 调用 |

三处非显然的选择：

| 选择 | 理由 |
|---|---|
| 表用 `STRICT` | 列类型写错当场报错，而不是 SQLite 的弱类型静默存进去 |
| `journal_mode = WAL` + `synchronous = NORMAL` | 探针要在服务运行时旁路直读；WAL 让读写不互斥。进程被杀时已提交事务仍在 WAL，满足本卡持久判据；掉电语义不在本卡（欠账） |
| 历史查询返回升序 | 「迟到者按发送顺序看到历史」是用户可见语义；在 SQL 里定死，不让调用方各自排序 |

注意：WAL 会在 `var/` 下产生 `wo.db-wal` / `wo.db-shm` 两个瞬时副产物。逻辑上仍是一个数据库，二者都在 `var/` 内且被忽略；不要把「一个文件」理解成目录里永远只有一个文件名。

`findRepoRoot`：从 `process.cwd()` 逐级向上找 `pnpm-workspace.yaml`，到根仍找不到就抛错并打印起始目录。探针会故意用 `cwd=apps/server` 启动服务，验证库仍落在仓库根 `var/`。

### 4.3 WebSocket 层：`apps/server/src/modules/collab/collab-ws.service.ts`

单进程、同一端口：不另起 HTTP server，而是在 Nest 的 HTTP server 上挂 `upgrade`。

```ts
onApplicationBootstrap() {
  const server = this.adapters.httpAdapter.getHttpServer() as HttpServer;
  this.wss = new WebSocketServer({ noServer: true, maxPayload: 64 * 1024 });
  this.upgradeHandler = (req, socket, head) => {
    const docId = parseDocId(req.url);
    if (docId === null) {
      socket.write('HTTP/1.1 404 Not Found\r\nConnection: close\r\n\r\n');
      socket.destroy();
      return;
    }
    this.wss!.handleUpgrade(req, socket, head, (ws) => this.attach(ws, docId));
  };
  server.on('upgrade', this.upgradeHandler);
}
```

- 注入 `HttpAdapterHost` 与 `WoDb`；`onApplicationBootstrap` 时 HTTP server 已创建但尚未 `listen`，挂监听时机正确。
- `parseDocId`：只接受 `^/ws/collab/([^/]+)$`，`decodeURIComponent` 后必须匹配 `^[A-Za-z0-9_-]{1,64}$`；其余路径/ID 一律 404 + destroy（没有其它 upgrade 消费者，不能把 socket 挂着）。
- 房间：`Map<docId, Set<WebSocket>>`；连接进房、关闭/出错出房，空集合删除。
- 进房先读库再发 `ready`；读库失败关 1011，不进房。
- 消息处理顺序**定死**：解析校验 → `db.append` → 给发送者 `ack` → 给同房其它 `OPEN` 连接广播。插入失败关 1011，**不发 ack、不广播**。
- 广播要逐个 peer `try/catch`：一个坏连接不能中断其余人的消息。
- 错误帧处理：二进制 → 1003；`JSON.parse` 失败 → 1003；形状不对/未知 type → 1008；文本为空或超过 4000 字符 → 1008；`maxPayload` 超限由 `ws` 自动 1009。
- 日志只记 docId、seq、关闭码，**不记消息正文**。
- `onApplicationShutdown`：终止所有客户端、关 `wss`、摘掉 `upgrade` 监听。`WoDb` 自己负责关库。

### 4.4 V3.1 帧协议（自有 JSON，不是 openapi 的 lib0）

| 帧 | 方向 | 形状 | 说明 |
|---|---|---|---|
| `ready` | 服务端 → 客户端 | `{ type:'ready', docId, messages:[{seq,text,at}] }` | 最近 100 条，升序 |
| `message` | 客户端 → 服务端 | `{ type:'message', text }` | `docId` **只从 URL 取**，不信帧里的 |
| `ack` | 服务端 → 发送者 | `{ type:'ack', seq, at }` | 仅在入库成功后发送 |
| `message` | 服务端 → 同房其它人 | `{ type:'message', docId, seq, text, at }` | **不回给发送者**；发送者只有 ack |

`at` 为 epoch 毫秒。失败一律用关闭码表达，不发明 `4xxx` 业务码（那需要先改 openapi 再改 shared，超出本卡）：

| 关闭码 | 触发 |
|---|---|
| 1003 | 二进制帧 / JSON 解析失败 |
| 1008 | 帧形状不对、未知 type、文本长度非法 |
| 1009 | `maxPayload` 超限（`ws` 自动） |
| 1011 | 读库或写库失败 |

### 4.6 探针：`scripts/probe-server.mjs`

只用 Node 22 自带能力（`node:sqlite`、全局 `WebSocket`、`fetch`），不引入测试框架。

前置：

- 开头断言 `process.versions.node` 主版本为 22，否则给出「本探针需要 Node 22.22.2」并退出。
- 断言 `apps/server/dist/main.js` 存在；不存在就提示先 `pnpm --filter @wo/server build`。
- 清理 `var/wo.probe.db`、`-wal`、`-shm`；成功结束后再清理，失败保留并打印路径。
- 先探测 `3100`：若已有服务应答，直接失败并提示「端口被占用，先停旧服务」，**不杀未知进程**。

启动服务：

- `spawn(process.execPath, ['dist/main.js'], { cwd: 'apps/server' })`——故意用包目录作 cwd，验证库路径按仓库根解析。
- env：`WO_JWT_SECRET=probe`、`WO_DB_URL=var/wo.probe.db`、`WO_LICENSE_PUBLIC_KEY=probe`、`PORT=3100`、`LOG_LEVEL=warn`。
- 捕获 stdout/stderr；失败时打印尾部，避免「进程没起来但探针只说超时」。

判据执行顺序（每条打印 `[服务] OK ...`，任一失败 exit 1）：

| 编号 | 动作 | 断言 |
|---|---|---|
| P0 | `fetch http://127.0.0.1:3100/api/v1/health` | 200 **且** `content-type` 为 JSON **且** body 精确等于 `{status:'ok'}`（不是 HTML） |
| P1 | 检查文件位置 | `<repo>/var/wo.probe.db` 存在；`<repo>/apps/server/var/` 不存在 |
| ① | A、B 连 `doc-a` | 各自收到 `ready`，`docId` 正确，`messages` 为空 |
| ② | A 发 `hello-from-A` | A 收到 `ack{seq:1}`，**300ms 内没有收到 seq=1 的 message**；B 收到 `message{seq:1,text}` |
| ③ | B 发 `hello-from-B` | B 收到 ack seq=2；A 收到 message seq=2 |
| ④ | 旁路直读库 | `doc-a` 恰两行，文本与顺序为 `hello-from-A`、`hello-from-B`，seq 严格递增 |
| ⑤ | 查 `sqlite_master` 与列 | 业务表恰为 `['collab_messages']`；列为 `seq/doc_id/text/created_at` 且类型符合 |
| ⑥ | C 迟到连 `doc-a` | `ready.messages` 恰两条，升序，文本与前两条一致 |
| ⑦ | D 连 `doc-b`；随后 A 发 `isolation-ping` | B 与 C 收到 seq=3；D 的 `ready` 为空，且 300ms 内未收到任何 message |
| ⑧ | D 发非 JSON；E 发未知 type；F 连 `doc-b` 发 `survivor` | D 关闭码 1003；E 关闭码 1008；F 收到 ack seq=4；health 仍为 JSON ok（服务没死） |
| ⑨ | `child.kill()` 等退出，重开库 | 进程已退出；`doc-a` 3 行、`doc-b` 1 行，文本与 seq 完整 |

为什么 ⑦ 要「D 进房后再发一条」：若没有新消息，D 收不到任何东西是恒真的，判据等于没写。B/C 的收到是同一子句里的正向对照，证明这条消息确实被广播了。

为什么 ⑨ 用强杀而不是 SIGTERM：见 §2。强杀后仍能读到 4 行，说明 ack 之前数据已经提交，而不是攒在进程内存里。

## 5. 判据与反向对照

### 5.1 正向判据

即 §4.6 的 P0/P1 + ①~⑨，共 11 条。验收运行必须全绿，并保留探针完整输出。

### 5.2 每条为什么不会恒真

| 判据 | 可能被什么假绿骗过 | 本卡的防法 |
|---|---|---|
| P0 | 端口被别的服务占用（3000 的 HTML 200） | 断言 content-type + body 精确形状，不只看状态码 |
| P1 | 从 `apps/server` 启动，库悄悄建在包目录 | 故意用 `cwd=apps/server`，断言文件落在仓库根、包目录下不存在 |
| ② | 服务只给发送者回显，没有真正广播 | 发送者只允许收 ack；B 必须收到同 seq 的 message |
| ③ | 服务只在单向上工作 | 反向再发一条，由 A 收到 |
| ④ | 「消息在内存里对」被误当成入库 | 绕过应用代码，用独立连接直读库 |
| ⑤ | 表名对但形状错，或悄悄多建了表 | 精确断言表清单与列清单 |
| ⑥ | 历史来自房间内存，或历史为空也能过 | 迟到者必须拿到恰好两条、顺序正确的文本 |
| ⑦ | 根本没发消息，D 当然收不到 | D 进房后再发；B/C 必须收到（正向对照），D 必须收不到 |
| ⑧ | 服务遇到坏帧直接崩，客户端关闭码看起来也「断了」 | 同时断言 1003/1008 与「之后新连接仍能完成一次收发」 |
| ⑨ | ack 先于提交，进程一死消息就没了 | 强杀进程后重开库再读；④ 是运行中读，⑨ 是进程死后读 |

### 5.3 反向对照（至少一条，本卡要求三条）

每条**单独**改、单独跑、跑完立即回退；回退后用 `git diff` 确认只剩预期改动。红/绿分布与预期不符，说明判据定位不准，先修判据。

| 编号 | 一行破坏 | 预期变红 | 预期仍绿 | 证明什么 |
|---|---|---|---|---|
| R1 | `WoDb.append()` 不执行 INSERT，只返回一个假 seq | ④ ⑥ ⑨ | P0 P1 ① ② ③ ⑤ ⑦ ⑧ | 持久化判据真的在读库，而不是被 ack 骗过 |
| R2 | 广播循环直接跳过（只 ack 不转发） | ② ③ ⑦ | ④ ⑤ ⑥ ⑧ ⑨ | 实时判据真的在测扇出，而不是只看发送者自己的回包 |
| R3 | `WoDb.history()` 直接返回 `[]` | ⑥ | P0 P1 ① ② ③ ④ ⑤ ⑦ ⑧ ⑨ | 迟到者历史真的来自库，而不是房间内存 |
| R4（可选） | `append()` 在写库前抛错 | ② ③ ⑦ ⑧ ④ ⑥ ⑨ | P0 P1 ① ⑤ | ack 发生在提交之后；写失败不会假装成功 |

## 6. 欠账

1. **WS 契约偏离**：同一路径 `/ws/collab/{id}`，但无 ticket、JSON 帧而非 lib0、无 SYNC/AWARENESS/PING/LOAD/CONTROL/ROLE_UPGRADE。V3.2 迁主路径时收口；V5.1 前不得对外宣称符合 openapi。
2. **`collab_messages` 是验证期临时表**：不是最终的 `yjs_updates` / 快照模型；seq 是全局自增而非按 doc；无保留/清理策略。交付轨按 schema 重做。
3. **`node:sqlite` 是 experimental**：Node 小版本升级可能改 API；`engines <23` 限制了爆炸半径。交付轨换 TypeORM 时只换 `WoDb` 实现。
4. **无鉴权、无限流、无 Origin 校验**：只绑回环；V5.1 分享链接前必须补。
5. **无心跳 / ping-pong、无死连接回收、无重连与断点续传、无 awareness**：V3.3 / V3.4。
6. **持久性只对进程被杀成立**：`synchronous=NORMAL` 在掉电场景可能丢最后一次提交；磁盘满、只读文件系统未测。
7. **WAL 副产物**：`wo.db-wal` / `wo.db-shm` 与主文件同目录，均被 `var/` 忽略；关机/异常退出后残留属正常。
8. **配置注入是捷径**：`WoDb` 直接读 `WO_DB_URL`，没有 ConfigModule；交付轨统一注入时删掉这处重复。
9. **只有 E2E 探针，没有单测**：`WoDb` 与 WS 状态机没有 Jest 覆盖；本卡以端到端判据为准。
10. **docId 字符集受限**：`[A-Za-z0-9_-]{1,64}`；V5 分享链接若用其它形态需放宽。
11. **「两端」是 WS 客户端不是浏览器窗口**：Univer 双端同步与 V2 存下来的本地文档如何进入协同，属 V3.2。
12. **未在 `var/wo.db` 本体上跑验收**：探针用 `var/wo.probe.db` 隔离，避免覆盖用户数据；正式路径只做一次手工启动确认。

