## 1. 决策：方案 B（`@wo/shared` 泛型化）

交接件 §5 留了两条路，本包选 **B**：

| 方案 | 形状 | 代价 | 结论 |
|---|---|---|---|
| A｜放 `apps/web` | 签名直接用 `Partial<IWorkbookData>` | 零抽象成本；但「业务层只认它」退化为 web 内部约定，V3 要另定一套 | 未选 |
| **B｜放 `@wo/shared` 泛型化** | `DataSource<TDoc>`，shared 内不出现 Univer 类型 | 多一层泛型，`subscribe` 事件类型也要泛型化 | **选定** |

理由：V3 起服务端要存同一份快照，若 V2 定成 web 私有约定，V3 必然出现两套接口并存——那是**比多一层泛型贵得多**的代价。泛型在 V2 只增加一个类型参数，收益在 V3 兑现，属于用一次性成本买掉未来分叉。

## 2. 两个被实测推翻的假设（本包最值钱的部分）

### 2.1 「异步 load 会撞碎 V1.2.1 的同步装配」——不必撞

交接件 §3.2 判断：`load` 变 Promise 后 effect 无法同步 `mountSheet`，WeakMap 记不住「正在建的 Promise」，双次 effect 会建出两张表。

**实测结论：实例与工作簿是两层生命周期。** 同一 Univer 实例内 `univerAPI.disposeUnit(id)` + `univerAPI.createWorkbook(data)` 可整体换数据，**渲染根不受影响**。

于是装配顺序定为「同步立实例挂空表 → 异步换单元灌数据」，`mountSheet` 仍是同步调用，WeakMap 仍只记已建实例，方案 C 的前提一条没破。**结构风险消解于「不改结构」。**

实测四条判据（一次性 spike，验完即删，未进提交）：

```
换单元前: {"unitId":"wo-demo-book","a1":1,"a3":3,"canvases":3}
① disposeUnit:  {"disposed":true,"stillThere":false}
② createWorkbook: {"created":"spike-book-2","got":true}
③④ 换单元后: {"a1":777,"a3":785,"canvases":3,"gridCanvasArea":{"w":1344,"h":587}}
```

A3=785 是 `=SUM(A1:A2)` 在新快照上现算出来的，不是搬过去的常量；截图 `C:/tmp/spike-swap-unit.png` 显示界面完好、无白屏。

### 2.2 「数据后灌 = 调 `setWorkbookData`」——没有这个方法

交接件方向 1 写「`load` 完成后再 `setWorkbookData` 灌入」。查 `@univerjs/sheets@1.2.0` 的 `f-workbook.d.ts`：`FWorkbook` 只有 `save(): IWorkbookData`，**没有任何原地覆盖方法**。

故「后灌」只能实现为**换单元**（销毁旧 + 建新），这也解释了为什么 2.1 的 spike 是必做而非可选——若不先验它，写到一半才发现方向 1 的实现手段不存在。

## 3. 接口定稿

`packages/shared/src/data/data-source.ts`，三方法：

| 方法 | 语义 | 刻意「不做什么」 |
|---|---|---|
| `load(docId)` | 返回快照；**文档不存在返回 `null`**，存储故障**抛错** | 不返回默认文档掩盖缺失——否则「新文档」与「读失败」在调用方看来一样，V2.3 的降级判据失效 |
| `save(docId, doc)` | 整体覆盖写，返回 `{ savedAt, bytes? }` | 不做字段级 merge——合并需要知道文档结构，而接口刻意不知道 |
| `subscribe(listener)` | 只通知「文档被改动」，推 `{ doc, origin, changedAt }` | 不描述改了什么；增量差异归 V3 的 Yjs |

四个约定（都在探针里有对应断言）：

1. **时间戳一律 epoch 毫秒 `number`**，不用 `Date`——`Date` 过 JSON 会变字符串，是类型与运行时不一致的经典来源。
2. **`origin` 三值**：`local-save` / `remote` / `external`。本端 save 也推 `local-save`，由监听方过滤——比让监听方自己记账「哪些是我写的」更不易漏。
3. **取消订阅必须幂等**（重复调用不抛错）。
4. **`load` 返回副本**，实现方负责克隆。

## 4. 装配实现

- `apps/web/src/sheet/attach-data-source.ts`（新增）：`attachDataSource()` 同步返回 `{ handle, isLoaded, detach }`，内部异步 `load` 后 `replaceDoc`。带 `generation` 守卫——回调回来时若组件已卸载/已 detach 则丢弃结果。
- `apps/web/src/sheet/mount-sheet.ts`：`SheetHandle` 增 `replaceDoc`；**所有取值器改经 `current` 间接访问**（直接闭包捕获初始 `workbook` 会在换单元后静默读旧单元——这是最容易漏的一处）。
- `apps/web/src/data/memory-data-source.ts`（新增）：内存实现，仅作接口验证桩，**不声称持久化**。
- `apps/web/src/sheet/SheetHost.tsx`：改走 `attachDataSource`；空表刻意**不带演示单元格**，否则「加载成功」与「降级空表」画面一样，V2.3 失去区分能力。

## 5. 判据与反向对照

探针 `--data-source` 十条：

```
[数据源] OK  ① 空表先挂、数据后灌（mount 早于 replace）｜mount@306ms｜replace@326ms
[数据源] OK  ② 数据经 load 流入并触发换单元｜轨迹 mount → load:start → load:end → replace
[数据源] OK  ③ 换单元后公式照常计算｜A3=3｜期望 3
[数据源] OK  ④ 换单元未拆渲染根｜canvas=3
[数据源·接口] OK  ① load 不存在返回 null
[数据源·接口] OK  ② save→load 往返一致
[数据源·接口] OK  ③ load 返回副本（改它不污染存储）
[数据源·接口] OK  ④ subscribe 收到 local-save
[数据源·接口] OK  ⑤ 取消订阅后不再收事件
[数据源·接口] OK  ⑥ 取消订阅幂等
```

**为什么不能只看「A1=1」**：把 demo 数据直接传给 `mountSheet`（完全绕开 DataSource）也能得到一模一样的画面。故判据落在装配轨迹 `__woAttachTrace` 上——它由装配层自己记录，业务代码伪造不出「先 mount 空表、后 replace」这个顺序。

**两条反向对照（证明判据真会变红，不是摆设）**：

| 破坏方式 | 结果 |
|---|---|
| `load` 改返回引用不克隆 | 只有**接口③**变红，其余九条全绿 → 定位精确 |
| 删掉 `trace('mount')`（模拟「等数据到了才挂载」） | 只有**判据①**变红，②③④ 仍绿 → **证实只靠画面无法分辨装配顺序** |

第二条尤其关键：它说明判据①不是冗余的，而是唯一能看见「结构顺序」的眼睛。

## 6. 顺带修掉的门口缺陷

```

失败：packages\shared\src\__negctl.ts 不得 import undefined        ← 修前
```

同时记录一条实测：**规则 H 扫原始文本，注释里的被禁 import 示例同样命中**。本包写注释时抄了那条 import 作反例，直接让门禁变红。已在注释里写明此事，并改为不复述被禁原文。

## 9. 欠账（收口时填）

1. **内存桩不是持久化**。V2 的 H2 假设（关掉浏览器内容还在）**完全未验**，本包不碰——由 V2.2/V2.3 承担。任何把本包当作「能存了」的解读都是误读。
2. **`save` 尚无调用方**。本包只验了接口能用（探针直调），编辑器改动→保存这条链未接（V2.2 做节流自动保存）。
3. **`subscribe` 的 `remote` / `external` 两个 origin 无产者**。形状已定，V2.2（跨标签页）/ V3（协同）才会真正产生。
4. **并发 save 的串行化只写在注释里，内存桩未实现**。IndexedDB 实现必须做——单条 Promise 链即可，但本包没验，V2.2 要补断言。
5. **滚动位置恢复未涉及**（V2.3 的范围）。
6. **`detach()` 无调用点**。与 V1.2.1 的欠账同源：路由化/多文档才需要，届时一并接。
7. **未验「两次 effect 是否只跑一次 load」**。本包靠 WeakMap 命中复用保证，但没做 StrictMode 专门断言；若将来把 `attachments` 换成别的作用域，这条会失守。
