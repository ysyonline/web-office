## 2. 三例的 Excel 判据（先定值，后比对）

| # | 场景 | 输入 | Excel 语义 | 期望 |
|---|---|---|---|---|
| ① | 空单元格参与 SUM | A10=10、A11 空、A12=20 | 空按 0 计 | **30** |
| ② | 文本参与 SUM | A14=`abc`、A15=`'5'`、A16=7 | 区域内文本一律忽略，**连像数字的文本也不折算** | **7** |
| ③ | 跨合并区求和 | A18:B19 合并，左上 A18=3，其余三格为空 | 合并区只有左上格存值 | **3** |

② 是最容易翻车的一条：若引擎把 `'5'` 折算成 5，结果是 12，而「12 看起来也合理」——所以必须先在
Excel 里定死 7。③ 同理：若四格都写了 3，SUM 也等于 3，但那是完全不同的数据形态。

## 3. 两条旁证：防止「结果碰巧对」

主断言只比数字，会漏掉「结果对但前提不成立」的情况。故各配一条旁证，与主断言并列：

1. **文本格必须仍以字符串存值**（`typeof getValue('A15') === 'string'`）。
   若 `'5'` 在载入时就被强转成数字，② 的输入条件已不成立，7 便不能归功于「忽略文本」。
2. **合并区内部必须为空**（`B19 === null`）。四格都写 3 时 ③ 同样得 3，旁证把这条歧义排掉。

两条旁证都进 pass 条件——它们不是「顺便打印」，是断言可信度的组成部分。

## 4. 规格

数据全部写在 `demo-workbook.ts`（与 V1.3.1 同一份），布局见该文件头部的表。要点：

## 7. 欠账（收口时填）

1. **三例只是「区域内的边界」，未覆盖运算级边界**：除零、循环引用、`#REF!`、超范围、
   文本数字混合的 `SUM` 与 `SUMPRODUCT` 差异均未测。本包按 ROADMAP 只做指定的三例。
2. **未做与真实 Excel 文件的逐例对照**：期望值来自 Excel 语义（人工判定），不是从 xlsx 里读出来的。
   严谨做法是造一个 xlsx、用 Excel 算出三例结果、导出缓存值比对——归 V4（导入解析做完才有这个能力）。
3. **合并区与公式的范围坐标只验了一处**（A18:B19）。多合并区相邻、重叠、以及合并区跨冻结线未测。
4. **文本对齐是渲染推断**：截图里 `'5'` 左对齐被当作「确实是文本」的肉眼旁证，实际判据靠 `typeof`，
   截图只作辅助。
