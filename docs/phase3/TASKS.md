拆包规则（脚本强制执行，非人工估算）：

```
包数 n = round(工时 / 1.1)，并强制 工时/n ∈ [1.0, 1.2]
包内五段：接口与骨架 → 主路径实现 → 边界与错误 → 测试与自检 → 联调与收口
          （n<5 时尾部合并，n>5 时按比例归段；设计卡用四段专用标签）
```

实测校准：788 包的工时分布见生成器输出，合计与工作项工时完全对账（**882.0h**）；包均越出 1.0~1.2h 带的仅 P3-011 六包（按实体内容切分，已在生成器 `BAND_EXCEPTIONS` 显式登记理由，见 §1 拆包规则注）。
> 注：D1 卡工时必须是 **1.2h 的整数倍**（2.4/3.6/4.8h = 2/3/4 包），否则 1.5h 这类数值会掉进「除不尽 1.0~1.2h」的死循环。这是 v1.0 已踩过的坑。

## 4. 派发包规范

每个包按固定五段切，派单时只给这一包的范围，不给整个工作项：

| 段 | 内容要求 | 收敛判据 |
|---|---|---|
| 接口与骨架 | 签名/类型/路由/表结构先落定，可空实现 | 编译通过，调用方已按接口写 |
| 主路径实现 | 正常流程打通（一条 happy path） | 手工跑通一次并留可复现记录 |
| 边界与错误 | 空值/超限/超时/并发/权限，逐条映射错误码 | 每条边界有断言或验证记录，无裸 500、无静默吞错 |
| 测试与自检 | 该段新增逻辑的单元测试或断言脚本 | 测试跑绿，且断言非恒真（至少一条「错误输入必须失败」的用例） |
| 联调与收口 | 与上下游对接、文档/注释补齐、遗留登记 | 工作项收口断言全过，遗留项进 OPEN-DECISIONS |

**包级 vs 工作项级（v1.1 修）**：CSV 分 `包级交付物/包级验收断言`（每包独有，段级模板）与 `工作项交付物/工作项收口断言`（工作项级，仅末包强制）。同一段内有多包时，包级断言强制填**锚点三项**——产出物路径 / 检查命令 / 通过判据，且同段内不得重叠。这是「1 包可独立验收」的最低机械约束。

派单必须带四件套（否则退回）：**① 本包范围 ② 包级验收断言 + 锚点三项 ③ 依赖包已完成的证据 ④ 本缝设计卡引用（有卡时）**。

### 4bis. 设计卡（D1）—— v1.1 新增

工作流自 v1.1 起是三段式：**设计卡（限缝）→ 包内五段（含接口与骨架先行）→ 边写边定（仅限卡未覆盖的低风险决策）**。

- **13 张卡、42.0h、覆盖 49 个工作项 / 417 包（52.9%）**；规范与清单见 `docs/phase3/DESIGN-LAYER.md` v1.2。
- 卡是**一批包的公共前提**，不是文档工程：一页上限、四栏固定（接口/数据结构｜时序或状态机｜错误码映射｜验收断言补充）、每条决策带出处。
- 排期**随批次前置**（**B1 开头 D1-13**、B2 开头三张、B3 开头一张、B4 开头三张、B5 开头三张、B6 开头两张），不做集中设计阶段。
- 派发校验：消费方首包「本包范围」未引用卡号 → 退回；卡未定稿 → 该缝的包全部不派。**v1.3 起该引用由生成器自动写入**（形如 `…（1/7）：接口与骨架｜前置设计卡：D1-13（docs/phase3/design/）`），单一来源是 ITEMS 的 `deps` 列——即在 deps 里写了卡号的工作项，其首包必然带卡号，不存在「文档说有、台账没有」的第二种状态。

## 6. 我做的四个判断，你可以直接推翻

1. **把「工程化基线 7 项缺口」当成 4h 的正式工作项（P3-001），而不是评审会附赠**。理由是它是 B1 全部前端包的前置：组件库不定，P3-033/P3-060/P3-062/P3-065 全部要返工。评审会需要一份裁决记录落盘，这就是 4h 的去处。
2. **金仓冒烟给 8h 而不是 REVIEW-CLOSING 写的 1 人日（8h）——数字一致，但我把它拆成 7 包后含「失败项回溯清单」**。冒烟本身可能 4h 就完了，剩下 4h 是给「万一 RETURNING 不兼容」的回溯与方言层改写预留，不给这个余量，爆雷当天没有预算处理。
3. **导入导出给 150h，比 plan.md 的 16 人日（128h）多 22h**。差额是我加的：CI 门禁接入（P3-115）+ 往返 Excel 打开验证（P3-113）+ 队列/512MB 上限（P3-114，plan.md 提了但没计工时）。plan.md 的 16 人日是「转换层」口径，不含工程化配套。
4. **设计层按「设计缝」出 13 张卡（42.0h），而不是按工作项出 47 张（94h）**。理由：同一决策写 47 遍，漂移风险高于它要补的缺口；而缺口是真实存在的——v1.0 的工作流只有「接口与骨架」这层包内纪律，跨包的时序/状态机/错误码无处承载。判据、清单与边界见 `DESIGN-LAYER.md`。**v1.2 补的 D1-13 是这套判据的回头验证**：P3-001 落定 zod 单一源后，校验链与契约门禁的时序/码段/门禁被 3 个工作项共 22 包消费、且编译器一条都约束不了（漏挂 pipe 不报错、命名错不报错、孤儿 schema 不报错），按 §1.1 判据出卡是判据本身的要求，不是追加。

### 7bis. k_D1 实测回填（2026-10-22，D1-13 卡定稿后执行）

**测量口径**（本项目唯一可机器复核的工时证据源）：会话录像 `~/.workbuddy/projects/d-code-web-office/*.jsonl` 的毫秒级 `timestamp`，取 D1-13 相关会话；**跨会话并行区间取并集**（两窗口同时活跃只计一次）；相邻消息间隔 >20min 视为中断不计（实测该空档内另一窗口在活跃，属真实的并行分摊而非空闲）。

**k_D1 = 2.66 / 2.4 = 1.11**（`python scripts/session-effort.py --kw D1-13 --kw P3-001 --session 7599b883:0.23 --session 1fa4bcd4:1.0 --session bd4dff1e:1.0 --session 07bcee24:1.0 --estimate 2.4` 可复现）。敏感度：初稿归属取 0 → k=0.98；取 0.5h → k=1.19；把并行窗口误当重复记账剔除 → k=0.53（不采信：该窗口有独立产出物）。**合理区间 k ∈ [0.98, 1.19]，全落在 1.5 阈值内。**

**处置（按本节原机制）**：

1. **不触发乘系数**：其余 12 卡（39.6h）维持原估。硬按区间上限 1.19 全域重估 = 47.1h（+7.5h，占 808.0h 的 0.9%），但需同步重算 722 包的包数 / 里程碑 / 泳道全部派生数字，收益低于估算自身误差，**不划算，不做**。
2. **实测构成必须写进卡的标准工时**：2.4h 中「起草 + 落盘」实测仅 ≈0.4h，**审查 / 挑刺 / 回执 ≈2.25h（85%）**。原估算把 85% 隐含在「冲突消解与落盘对齐」段内未明说——这正是需要 k 才能发现的原因。余下 12 卡按「起草 0.4h + 审查 2.0h」结构分配；**若某卡再撞历史包袱（D1-05 码段撞车、openapi 400 覆盖缺口一类），按单卡 +1.2h（1 包）上调，不开全局乘数**。
3. **样本偏差（诚实登记）**：D1-13 是**最脏的一张卡**——同日撞上 7xxx 放行未传导、registry 码段撞车、openapi 400 覆盖缺口三件历史包袱，拿它当样本得到的是**上限值**。因此 k_D1 ≤ 1.5 只能说明「不需要全局乘数」，**不能反推「其余 12 卡一定够用」**；逐卡复核仍按 OPEN-DECISIONS 既有归属执行。
4. **口径增量**：本测量方法（会话录像时间戳 + 并行取并集 + 20min 中断阈值）可复用于 E3 前端包（P3-060~P3-066）与交付验收的 k 回填，不再依赖「回忆录式」估时。

CSV 字段（16 列）：`包号 / 包ID / 里程碑 / 需求域 / 工作项ID / 工作项 / 泳道 / 包序 / 工时h / 本包范围 / 包级交付物 / 包级验收断言 / 工作项交付物 / 工作项收口断言 / 依赖包 / 状态`。

派发时把该行改 `状态=已派发`，回传验收后改 `完成`——状态列就是进度看板，不需要另立跟踪表。设计卡包的状态同样走这两态，未 `完成` 时其消费方首包不得派发。
