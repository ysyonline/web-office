## 0. 结论（先给出裁定）

**v1.0 的工作流里没有独立设计环节，只有半个替代物。**

| 层级 | v1.0 有什么 | 实际解决什么 | 没解决什么 |
|---|---|---|---|
| 契约层 | Spec / ADR-001~003 / schema.md / openapi / plan.md / pages.md | 跨版本、跨里程碑的**稳定决策** | 决策的**消费视图**：某个人拿到某包时该遵守哪些结论、顺序如何 |
| 任务层 | TASKS §4「派发包五段」第一段「接口与骨架」 | 签名/类型/路由/表结构**先行落定**，编译通过，调用方按接口写 | 跨包共享的**时序、状态机、错误码映射、投影规则、降级政策** |
| 代码层 | 边写边定 | — | 无承载处，靠口头对齐 |

核查依据：全库 grep `详细设计 / 技术设计 / 开发设计 / 接口契约 / design doc` **零命中**，说明这是空白，不是藏在别处。

## 1. 判据：什么决策才配一张卡（第一性原理 + 对抗式）

### 1.1 第一性原理

设计文档唯一不可替代的价值：**一个决策被 ≥2 个独立执行者消费，且该决策无法由编译器或测试自动约束。**

由此推出三条排除：

1. 只有 1 个消费者 → 归该包的「接口与骨架」段（v1.0 已有纪律），写卡是浪费；
2. 能被类型系统约束 → 归 `packages/shared`（P3-010 已建载体），写卡是重复；
3. 剩下的才是卡的领地：**时序/顺序、状态机、错误码映射、投影规则、降级政策**——这些错了编译器不报错，测试也只在恰好覆盖时才报。

判据落成一句可操作的话：*同一决策若写错，会导致两个以上包各自实现出不同版本 → 必须出卡。*

### 1.2 被否决的两个方案（对抗式记录）

| 方案 | 成本 | 否决理由 |
|---|---|---|
| A. 按工作项铺开（47 项 × 2.0h） | 94h / 10.9% | ① 同一决策会在 47 张卡里重复表述，**漂移风险高于它要补的缺口**；② 1.5h/项不可拆（1.5÷1=1.5 超上限、÷2=0.75 低于下限），只有 2.0h 倍数是合法粒度，等于被迫把粒度拧到与决策无关的尺寸 |
| B. 不设设计层，把「接口与骨架」段写厚 | 0h | 该段是**包内视角**，看不到邻包；分支 C 的「三重应用错位」（cellData/档案/oplog 三通道谁先应用）就是这个缺口的实证——14 个包各自「按接口写完」，仍会错 |

### 1.3 缺口的代价（若一张卡都不做）

| 域 | 风险密度 | 具体失败模式 |
|---|---|---|
| R3 协同（16 项 / 138h） | 最高 | 双通道顺序、抑制标志、close 码语义各写一份 → 收敛模型失效，且**只在并发下暴露** |
| R4 导入导出（17 项 / 150h） | 最高 | 四桶判定顺序、档案键迁移、投影规则各写一份 → 静默数据损坏（分支 C 的 P0 已实证过路径） |
| R6 交付（8 项 / 84h） | 中 | AC→用例→环境无追溯矩阵 → 验收阶段才发现某条 AC 无人认领 |
| R1/R2 | 低 | 单包可闭环，已在「接口与骨架」段覆盖 |

## 2. 设计卡规范

### 2.1 四栏（固定，不得增删）

| 栏 | 内容 | 完成判据 |
|---|---|---|
| ① 接口 / 数据结构 | 签名、类型、消息形状、表/字段、键形态 | 消费方可直接照抄，无需再问 |
| ② 时序 或 状态机 | 参与者、消息序、失败分支、回滚点；或状态 × 事件迁移表 | 可执行描述（不是「大致这样」） |
| ③ 错误码映射 | 每条边界 → 错误码 → HTTP/WS close → 用户可见文案 | 与 D1-05 四层矩阵一致，无新增未登记码 |
| ④ 验收断言补充 | 该缝上**模板断言无法表达**的包级断言 | 每条可执行，且能指到具体包号 |

### 2.2 硬约束（违反即退回）

1. **一页上限**。超一页即拆卡，不允许长成「设计文档」——长文档没人读，等于没写。**体量以字符数度量，不以行数度量**（行数可稳定而单行膨胀：D1-13 的 E-CV 单行实测 739 字符）。
2. **每栏必填**，不涉及的写「本卡不涉及 + 理由」。空栏 = 未完成。
3. **每条决策带出处**（Spec/§、ADR-00x/§、schema.md/§、plan.md 行号）或标「本卡新定」。
4. **「本卡新定」若与既有契约冲突 → 开 OPEN-DECISIONS，不得私改契约**（沿用 REVIEW-CLOSING 的契约纪律）。
5. **第四栏不回写 backlog.csv**。台账单一数据源，卡上的补充断言在派单时随包附带；否则台账与卡双源必然漂移。
6. 落盘路径 `docs/phase3/design/D1-xx-<slug>.md`，消费方首包「本包范围」引用卡号——**未引用即视为卡未完成**（生成器已把 D1 依赖写进 `依赖包` 列，可直接做派发校验）。
7. **出处不引行号**。凡引 openapi/schema.md 等活跃变更文件，一律按 **schema 名 / §符号** grep，不写行号——行号在每次契约落盘后结构性漂移（D1-13 卡曾引 `LoginRequest@1039`，实为 1162；`ShareCreateRequest@1284` → 1415），「出处带行号」在本仓库不可持续，且会伪装成精确引文（2026-10-22 挑刺 P2-3 / N-1 顺带）。
8. **出卡四步（固定流程）**：读本文件 §2.1/§2.2 + 对应任务书 → 按 schema 名/§符号 grep 全部出处（条 7）→ Write 四栏卡 → 收口跑门禁三连（`node scripts/verify.mjs` → `python -X utf8 scripts/check_openapi_contract.py` → `python -X utf8 scripts/gen_status_panel.py`，口径见 ANCHORS.md §0）。

### 3.2 每张卡必须定死的决策（卡的核心内容）

**D1-05 错误码与降级四层矩阵**（做在 B2 最前，是三张卡的前置）
1. 码段分配：**以 openapi `x-error-code-registry` 已放行实况为事实源，D1-05 无权重分配**——1xxx 认证与用户 / 2xxx 文件域 / 3xxx 导入 / 4xxx 协同与连接 / 5xxx License / 6xxx SSO / 7xxx 请求校验 / 9xxx 兜底（v1.3 改：原任务书写「1xxx 通用 / 2xxx 认证与权限」且缺 6xxx，与 2026-10-22 用户放行实况相反，挑刺 P0-2；若 D1-05 设计中发现 registry 确有缺陷，走解冻流程 + OPEN 条目，不得私改）。
2. 四层对照：HTTP status ↔ 业务 code ↔ WS close（4409 只读降级 / 4410 超连接 / 4411 席位释放 / 4412 内存水位）↔ 前端呈现档位。
3. 同语义多出口一致：License 超席必须同时定义 HTTP 402、WS 4409、Command 守卫三个出口的等价语义，任一出口单独实现即视为不一致。
4. 前端呈现三档：toast（可继续）/ 页内态（阻断单操作）/ 全屏阻断（会话失效）——判定条件写死。

**D1-11 配置装载与启动断言链**
1. 配置键三分类（必填 / 可选有默认 / 派生），必填缺失 = 启动失败并指名键，可选缺失 = 显式降级日志。
2. 三级国密断言（sm3 / SM2 曲线 / 自签自验）的失败语义 = 拒绝启动、退出码非 0；离线包形态**不提供跳过开关**（跳过开关即安全后门）。
3. 容器 vs 裸机两形态的环境变量差异清单与默认值来源（镜像内 vs 挂载配置文件）。
4. 健康检查分级：liveness（进程活）/ readiness（依赖可用：库、License、离线源），readiness 失败不得触发重启。

**D1-09 认证与 token 生命周期**
1. access 15min / refresh 7d 的刷新时序：并发请求的刷新去重（单飞）与失败传播。
2. 失效传播方式：refresh 轮换 + 服务端失效集（禁用用户、改密、登出）——禁用后既有 access 的放行窗口长度写死。
3. WS ticket 5s 一次性票据与 access 的关系：票据只做握手凭证，**不复用 access 刷新逻辑**（避免握手期刷新引发连接风暴）。
4. 锁定（5 次失败 15 分钟）与首登改密对既有会话的交互：锁定期内已签发 access 是否放行（等保口径 → 拒）。

**D1-07 前端状态分层与乐观更新**
1. 状态归属清单：哪些状态在 zustand、哪些只在 Univer 内部、**哪些绝不允许双写**（双写=协同回声的根因）。
2. 乐观更新的提交点与回滚点（以服务端 ack 为界），失败回滚的表现（内容回退 + toast + 不吞错）。
3. 只读降级的**单一事实源**（License 402 / WS 4409 / 权限不足三源合一），banner 与编辑器可编辑态均从这里读。
4. 任务类状态（导入/导出/保存）的推进方式：轮询（间隔与退避）vs WS 推送，二选一并说明依据。

**D1-01 协同三通道时序与抑制矩阵**
1. 三通道分工与先后：cellData（内容 Y.Map）→ 档案侧车 → 结构 oplog；**本地先内容后档案，远端回放后档案**。
2. 抑制矩阵：`onlyLocal` / `fromCollab` / `isUndoRedo` 三种来源 × 六个应用点的取值表（分支 C 实测踩过三重应用错位）。
3. 一 op 一 update 帧的合并边界：哪些连续操作必须合并（避免帧爆炸），合并后如何保持单事务语义。
4. doc-rebuild 期间的写操作语义：拒绝（返回哪个码）还是排队，队列上界。
5. 回声放大防线：服务端广播的 origin 过滤规则。

**D1-06 快照物化与加载状态机**
1. doc 生命周期状态机：未加载 → 加载中 → 活跃 → 已物化 → 驱逐中 → 重建；每个迁移的触发事件与失败回退。
2. base_seq 事务边界：快照与 base_seq 同事务；物化三条件（时间/条数/水位）的短路顺序。
3. LRU 驱逐与写入互斥：引用计数 or 驱逐锁，二选一；驱逐失败时的重试与告警。
4. 加载就绪信号：snapshot 下发 → 增量回放 → 就绪；客户端重放幂等（重复 seq 丢弃）。
5. SIGTERM drain 与物化的关系：**drain 期间不强制物化**（增量已持久化，物化是重操作会放大 drain 风险）。

**D1-08 连接与席位状态机**
1. 连接状态机：connecting → authed → view/edit → readonly → closed(reason)；close 码与状态一一对应。
2. 同账号多连接的席位归属（按连接还是按用户）与超连接踢出顺序（第 4 连接 4410）。
3. 满席时新编辑请求的处置：转只读（4409）而非拒入——与「已有编辑不中断」配套。
4. 断线宽限期的语义只在本卡定义一次（60s，服务端接口不焊死该数值，只暴露占席/释放/用量）。

**D1-04 IR↔snapshot 双向投影规则表**
1. 类型矩阵：cell type ↔ `ICellData.t/v/f/s` 的映射与不可表达项的降级去向。
2. 样式矩阵：字重/字号/字体色/底色/对齐/换行/四象限边框/合并/numFmt ↔ Univer style 字段；theme 色换算口径。
3. 日期/时长/百分比/科学计数的「存储值 vs 显示值」分离规则（numFmt 代码保真）。
4. 不可表达项降级清单：导出侧写回什么（保真 / 近似 / 丢弃 + 说明），逐项对应 AC-08 的「无修复弹窗」。

**D1-03 导入四桶判定与降级政策**
1. 判定顺序与短路：W（白名单 119）→ X（排除集 8）→ 桶 II（引擎未实现）→ 差分；短路点写死。
2. 每类在 snapshot 的表达：保 f / 剥 f 存档 / 剥 f 丢 f（三选一，逐类给例）。
3. 降级原因码枚举与用户可见文案一一对应；提示条 N 的计数口径与 UI 一致（P3-093 依赖此口径）。
4. 差分规则细节：相对容差 1e-10、万格上限超限行为（走冻结）、volatile 导入静态化。

**D1-02 档案坐标键生命周期与迁移**
1. 键形态 `formula-archive:{sheetId}:{row}:{col}` 中 sheetId 是 local 还是 global id；重命名/复制/删除 sheet 时的行为。
2. 六类结构 op × 正反向的键迁移公式：插入/删除行列、排序、移动、剪切粘贴、合并；undo/redo 反向迁移（undo 实测触发 `remove-rows` **复数**形态，双形态收录）。
3. 导出前置校验：目标格 `v !== 档案 v` 的丢弃与降级说明（数据安全优先于文本保真）。
4. 事务边界：档案与 cellData 在同一 Y.Doc 事务内；双通道顺序与 D1-01 矩阵一致。
5. 陷阱用例入卡：**插入行后不撤销即导出**（插后立即 undo 会「碰巧对齐」，掩盖错位）。

**D1-10 License 判定链与时钟**
1. 判定链顺序：签名 → 载荷解析 → 到期 → 席位 → 只读降级；短路规则。
2. `max_seen_at` 更新时机（每次判定成功即写）与三档时钟处理：正常 / 回拨 ≤24h 告警 / >24h 仍告警但不误杀；判定取 `max(系统时钟, max_seen_at)`。
3. 宽限期（7 天）内的能力边界：只读 + 续期引导，不锁死。
4. 三层只读防线（服务端 402 / WS 4409 / Command 守卫 / UI banner）语义一致，与 D1-05 的四层矩阵对齐。
5. 商务口径引用 §6-bis 禁用语（不承诺防拷贝），技术侧不做与之矛盾的实现。

**D1-12 AC↔用例↔环境追溯矩阵**
1. AC-01~15 逐条的自动化脚本归属、执行环境（单机 / 双端 / 断网 / x86 / aarch64）、fixture。
2. AC-05 四档时延（L0/L1/L2/L2b）的采样方法、断言语义（P95、窗口大小、采样次数）。
3. 失败定位口径：输出必须含 AC 编号 + 断言行。
4. 不可自动化项（气隙抓包、国产浏览器内核）的替代证据模板（E1 手工记录格式）。

**D1-13 请求校验链与 API 契约生成门禁**（P3-001 评审后新增，排在 B1 最前）
1. schema 命名逐字对齐 openapi `components.schemas` 的 9 个契约项；非契约 schema 进 `src/schemas/internal/`，目录即分类。
2. `field = z.core.toDotPath(issue.path) || '(root)'`，根级 issue 一律 `(root)` 不区分 code；`rule` 取 `issue.code`。
3. 请求 schema 一律 `.strict()`（默认 strip 与 `additionalProperties:false` 矛盾，属沉默逻辑错误）；refine 必须显式传 path。
4. 7xxx 段四条码（7001 请求体 / 7002 查询越界 / 7003 JSON·multipart 非法 / 7004 路径参数）↔ HTTP 400 ↔ 前端四档呈现；**2026-10-22 已放行落盘，按逐码实现（区间兜底条款作废，v1.3 改）**。
5. 契约门禁：openapi.yaml 手写件为唯一事实源，`schemaOf()` 装饰器产物从属，G1 contract-diff **类型面归一化全等、不等即 fail、无 warn 档**（散文/x-\* 扩展不设「等」比对，见卡 ② 口径澄清）；孤儿 schema 一律 fail。
6. 漏挂防线：自研 pipe 不能全局注册 → `validation-coverage.e2e-spec.ts` 遍历 openapi 带 requestBody/query/path 的操作发非法样本，**按样本类型分流断言**（body→7001 / query 越界→7002 / path 非法→7004），并含 POST snapshot 空 body 的反断言（200/2005，不得 7001）。

## 8. 同期修复：backlog 包级断言缺陷（v1.0 遗留）

**缺陷**：v1.0 的 `交付物` / `验收断言` 是工作项级文本，被复制到该工作项每一个包——88 个多包工作项、687 包中 **0 个有包级区分**，验收只能落到 4~16h 的工作项粒度，与「1 包 1~1.2h 可独立验收」的设计意图冲突。

**修法（生成器 v1.1）**：
1. 新增段级模板：五段各有自己的交付物与断言（接口骨架→可编译且下游已按接口写；主路径→happy path 手工跑通并留记录；边界→逐条断言且映射错误码、无裸 500；测试→跑绿且非恒真；收口→联调 + 遗留登记）。
2. **同段多包必须填锚点三项**（产出物路径 / 检查命令 / 通过判据），且同段内不得重叠——这是把「包级可验收」变成可机械检查的最小约束。
3. CSV 列改为：`包级交付物 / 包级验收断言 / 工作项交付物 / 工作项收口断言`。工作项级断言只在末包强制，其余包看段级断言。
4. 顺带修第二个缺陷：v1.0 在 n<5 时**直接丢段**（n=4 的 9 个工作项丢「测试与自检」），n>5 用「增量实现」这种不承载纪律的空标签。v1.1 改为按比例归入五段，尾部合并。

**机器自检（每次重跑生成器输出）**：包级断言全同的多包工作项 = 0；依赖悬挂 = 0。

**遗留局限（诚实标注）**：段级模板是「纪律断言」，不是「事实断言」——它保证每个包能独立验收，但不保证断言内容对该包特有。真正特异的断言来自设计卡第 ④ 栏（13 张卡覆盖 402 包 / 55.7%）；剩余 320 包靠派单时填锚点三项。若要求 722 包全部特异，需为 101 个工作项手写五段断言（约 500 条），成本不低于 20h，当前不纳入，等首批派单后的实际摩擦决定是否追加。
