## 1. 裁决口径（五问，缺一即否决候选）

任何新增依赖必须先过这五问，答案写在落盘文本里：

1. **npm 官方源可取 + tarball 完整**（可镜像入 verdaccio）
2. **无固定 CDN 外链**（运行时零外链是 Spec AC-12 红线）
3. **无原生编译链**；若含原生二进制，须核实麒麟 V10 / 统信 UOS × x86_64 / aarch64 四象限产物可得
4. **许可证**：MIT / ISC / Apache-2.0 / BSD 放行；MPL 须标注；GPL / AGPL / SSPL 红线
5. **版本矩阵**：与 React 18.3 / Univer 1.0.2 / Vite 7 / Nest 11 / Node 22.22.2 无冲突

> **纪律纠偏（本轮两次同类问题）**：「信创原生二进制不可得」不能当作万能否决理由。前端实测 esbuild 0.28.2（Go 静态，零 GLIBC 符号）、rollup 4.64.12、rolldown 1.2.15、lightningcss 1.33.0、@tailwindcss/oxide 4.3.3 的 aarch64 产物**全部存在且 glibc 下限均为 2.17**（麒麟 V10 的 2.17/2.28、统信 UOS 的 2.28 全满足）。真实否决理由必须写准：
> - Tailwind v4 → 官方 browser-support 下限 **Chrome 111**，击穿本项目 Chromium 100+ 下限
> - Vite 8 → 依赖 rolldown + lightningcss（后者 **MPL-2.0**）两组必需路径且无 JS fallback，生态成熟度不足
> 用站不住的论据否决，后续有人拿实测数据翻案时会把正确结论一起推翻。

## 2. ①②③④ 裁决明细

### 2.1 ① React 组件库与样式层（前端主裁，team-lead 复核）

**裁决：自研外壳原子 + Radix 无样式行为原语 + Tailwind 3.4.19。不引入任何大而全组件库。**

| 项 | 结论 |
|----|------|
| 样式层 | Tailwind CSS **3.4.19**（PostCSS 模式）+ postcss 8.5.31 + autoprefixer 10.6.1 |
| 行为原语 | `@radix-ui/react-dialog` **1.3.1** / `react-dropdown-menu` **2.2.1** / `react-context-menu` **2.4.1** / `react-tooltip` **1.4.1** / `react-toast` **1.3.1** / `react-avatar` **1.3.1** / `react-tabs` **1.2.1** / `react-progress` **1.2.1** / `react-popover` **1.3.1** |
| 变体工具 | class-variance-authority 0.7.1 + tailwind-merge 3.7.0 + clsx 2.1.1 |
| 否决 | antd 5/6（hard dependency `@ant-design/icons` 第二图标源 + cssinjs 运行时 + 46MB）／Semi 2.104.0（拖入 @tiptap/* 约 20 包 + semi-icons，58.2MB）／Arco 2.66.18（自带 color/icon 子包）／**Mantine 9.7.3（peer react `^19.2.0`，与已锁 React 18.3.x 硬冲突）**／shadcn CLI（需联网拉 registry，且默认 Tailwind v4 + React 19 路径不适用；改为手工采纳其「源码入仓 + Radix」做法） |

**Radix 版本纪律**：Radix 各包主版本独立，**不存在「同代」概念**。dropdown-menu 与 context-menu 在 2.x 线，dialog / tooltip / toast / avatar / tabs / progress / popover 在 1.x 线。CI 加「Radix 系列版本必须与本表逐一相等」断言。

**Tailwind × Univer 1.0.2 冲突（前端 blocking，team-lead 已独立复核，属实）**

本机实测 Univer 1.0.2 三份 CSS（design 75.7KB / ui 52.2KB / sheets-ui 29.2KB，合计 1738 条规则）：

- **裸元素选择器仅 2 条**：`* { --univer-tw-*: ... }` 与 `* { scrollbar-color/width: initial }`
- **无 html / body 重置，无 preflight**
- `box-sizing` 只出现在 `.univer-box-border` 等**类选择器**上
- 确有 4 条针对 `>ul:not(:last-child)` 的菜单规则

因此 Tailwind preflight 一旦全局生效，会在三处与 Univer 对撞：① `*,::before,::after { box-sizing: border-box }` 改变 Univer DOM 默认盒模型 → canvas 与 overlay 错位；② `button,input,select,textarea { padding:0; font:inherit }` 清空公式栏与 zen-editor 的 padding/字体；③ `ol,ul,menu { list-style:none; margin:0; padding:0 }` 与 Univer 的 ul 菜单规则争用同一批元素，胜负取决于加载顺序，不可预测。

**强制规避（写进 B1 验收）**

1. `apps/web/tailwind.config.ts` 必须 `corePlugins: { preflight: false }`（硬要求，不接受「先开着看看」）
2. 自写 `.wo-shell` 作用域 reset（`apps/web/src/styles/preflight-scoped.css`），全部包在 `:where()` 内使特异性为 0；Univer 容器 `#univer-host` **不带** `.wo-shell`
3. CSS 引入顺序定死：`design-tokens.css` → `preflight-scoped.css` → `tailwind.css` → `@univerjs/*/lib/index.css`（Univer 官方要求其 CSS 最后加载）
4. Tailwind `content` 限定 `apps/web/src/**` 与 `packages/ui/src/**`，**必须排除 node_modules**（否则 @univerjs 包内文本被扫进产物）
5. 四条验证断言：V1 Univer 子树 `boxSizing` 保持 `content-box`／V2 canvas 与容器尺寸差 ≤1px／V3 preflight 开-关两次构建三区截图零差异／V4 产物 CSS 中 `box-sizing: border-box` 只允许出现在含 `.wo-shell` 或 `.univer-box-border` 的选择器内

**成本对比（数据，非感觉）**：自研 10~14 个原子约 **7~9 人日**（复杂四类 Dropdown/ContextMenu/Dialog/Toast 各 1.0~1.5，简单类各 0.5）；引入 antd 的一次性 token 桥接 **3~5 人日**但为**持续成本**（每次 token 变更需重验桥接 + 48 个直接依赖常驻镜像与许可证清单 + 图标双源长期靠 lint 拦截）。绝对值接近，但一端一次性、一端持续且依赖面差一个数量级 → 选自研。

**图标红线边界（team-lead 裁定，写入 Spec §4）**：`@univerjs/sheets-ui@1.0.2` 硬依赖 `@univerjs/icons@1.43.1`（引擎内置图标集，不可替换），与 Spec §4「lucide-react 全项目唯一图标来源」存在字面冲突。裁定口径：**红线只约束自研代码**；Univer 引擎内置图标属第三方渲染产物，不在红线范围内；但自研组件中**禁止 import `@univerjs/icons`**。

### 2.2 ② 表单 + 校验库（前端主裁 + 后端承接，team-lead 终裁）

**裁决：zod schema 单一源落 `packages/shared`；前端 `zodResolver` 消费，后端**自研 ZodValidationPipe**（约 30 行，零新依赖）消费。class-validator、class-transformer、nestjs-zod 三者均不进依赖树。**

| 侧 | 方案 |
|----|------|
| schema 落点 | `packages/shared/src/schemas/`（`LoginSchema` / `CreateUserSchema` / `SsoConfigSchema` / `FileCreateSchema` / `FileRenameSchema` / `ShareCreateSchema` / 各 Query schema / `PasswordRules`） |
| 前端 | react-hook-form 7.90.0 + `@hookform/resolvers` 6.0.0 的 `zodResolver`；类型用 `z.infer` |
| 后端 | 自研 `ZodValidationPipe`，逐参数挂载 `@Body(new ZodValidationPipe(LoginSchema))` |
| OpenAPI schema | zod 4.6.7 内置 `z.toJSONSchema(schema, { target: 'openapi-3.0' })`，封装为 `schemaOf()` 后喂 `@ApiBody` / `@ApiResponse` |
| 契约关系 | **openapi.yaml 仍是契约唯一事实源（(a) 不变）**；zod 只是校验规则单一源；两者由 CI G1 contract-diff 强制相等。未改 (c)，不重开冻结窗口 |

**nestjs-zod 降为回滚备选的理由**：其核心增量是「zod → OpenAPI schema 让 G1 的 components.schemas 比对成立」，而 zod 4.6.7 自身已提供 `target: 'openapi-3.0'`（实测输出无 `$schema`、无 `$defs`、`nullable` 用 OpenAPI 写法、int→integer、默认 `additionalProperties:false`），增量消失；剩余价值（DTO 自动 metadata、响应序列化）前者可显式写且漏写被 G1 抓红，后者明确不做。

**三个静默坑（前端实测 zod 4.6.7 `$ZodIssueCode` 共 11 个字面量，必须按此规避）**

1. `unrecognized_keys` 的 `path` 为空数组 → `field` 得到空字符串 → 前端 `setError("")` 无效、用户零反馈。规约：`field = i.code === 'unrecognized_keys' ? '(root)' : i.path.join('.')`，前端对 `'(root)'` 走 Toast 不进字段级
2. `.refine()` / `.superRefine()` 不显式传 `path` 时 `path` 亦为空（口令复杂度规则正踩此坑）。规约：shared 层所有 refine 必须显式传 `path`，CI 断言喂必失败样本后所有 issue 的 `path.length > 0` 或 `code === 'unrecognized_keys'`
3. `rule` 值域 11 个，前端只对 5 个做语义化文案，其余 6 个直接展示 schema 中的中文 `message`。配套断言 **V-S2**：每个 schema 喂必失败样本，断言 issue 的 `message` 不含 ASCII 字母序列（兜中文文案，防 zod 默认英文漏网）

**strict 语义（后端纠偏，采纳）**：`z.object()` 运行时默认 **strip**（静默剥离未知键）而非拒绝，与 `z.toJSONSchema` 输出的 `additionalProperties: false` 语义矛盾——文档说不允许、运行时却静默吞，属典型沉默逻辑错误。规约：新建用 `z.strictObject()`，`.extend()` 后再补 `.strict()`。

**验收断言 V-S1（schema 单一落点）**：① `apps/**` 内出现 `export const .*Schema = z.` 即 FAIL；② 所有 `ZodValidationPipe(XxxSchema)` / `zodResolver(XxxSchema)` 的 `XxxSchema` 必须解析到 `@wo/shared` 的导出。

**边界样本测试的落点（team-lead 裁定）**：夹具不搞前后端双 job（单一源下双跑无信息增量）。边界样本矩阵落 `packages/shared/__tests__`，由 Vitest 跑一次；后端侧改由 `apps/server/test/validation-coverage.e2e-spec.ts` 覆盖「pipe 是否漏挂」——自研 pipe 无法全局注册、漏挂即该端点零校验且不报错，故该 e2e 遍历 openapi 中带 requestBody/query 的端点发非法样本，断言 400 + code 7001。

## 3. 专家冲突与 team-lead 裁定

| # | 冲突 | 裁定 | 理由 |
|---|------|------|------|
| C1 | ② 事实源：后端 v2「zod 单一 schema 源」 vs 前端 v1.1「zod + class-validator 双写 + 共享夹具」 | **采纳 zod 单一 schema 源，撤双写** | 前端撤回的前提（走单一源即须把契约事实源改 (c)、重开冻结窗口）不成立——openapi.yaml 仍是契约事实源，zod 只是校验规则源，二者由 CI 强制相等。且双写即便配夹具，也只覆盖写进夹具的样本，未覆盖边界是静默区；单一源是结构性消除第二份定义 |

### 5.3 ⑦ monorepo 目录结构

| 项 | 结论 |
|----|------|
| 编排工具 | **不引入 turbo / Nx**，用 pnpm 内置 `pnpm -r` / `--filter` / `--parallel` |
| 否决 turbo 2.11.10 | optionalDeps 为平台原生包，且 **`@turbo/linux-arm64-musl` 实测不存在**（arm64 仅 glibc 一支，musl 底座一旦采用即失效）；另引入 turbo.json 配置面与缓存守护 |
| 否决 Nx | 原生覆盖面优于 turbo（arm64 的 glibc 与 musl 都在），但带来项目图/插件/缓存/云端一整张概念面；对 3~4 个 workspace 包收益≈0 |
| 复评触发器 | workspace 包数 >8，或 CI 单次构建 >10 分钟，或出现包级依赖图环 |
| workspace 协议 | 包名统一前缀 `@wo/*`；内部引用一律 `workspace:*`（catalog 条目用 `catalog:`） |
| shared 定位 | **允许含运行时代码**，限定为：DTO 类型、zod schema、错误码常量、纯函数（如协同配色用的 `fnv1a32(userId)` 确定性哈希）。禁止 React/Nest/univer/yjs 相关 import、禁止原生依赖、禁止 side-effect。**机械判据：`packages/shared/package.json` 的 `dependencies` 只允许出现 `zod`**，新增一个依赖须过架构师 |
| shared 构建 | **构建**（含运行时代码，不能源码直饮）：apps/web 走 Vite ESM、apps/server 走 Nest CJS，故用官方 `tsc` 两遍产出 `dist/esm` + `dist/cjs`，`exports` 双入口。**不引入 tsup/rollup**（tsup 会把 esbuild 拉进来），保持构建工具面 = Vite + tsc 两个已知量 |

**分层依赖规则（写进 P3-010 收口断言）**：`apps/*` 可依赖 `packages/*`；`packages/shared` 只依赖 zod；`packages/config` 零运行时依赖、不含业务；**反向依赖与跨 app 依赖一律禁止**（`scripts/` 加一条依赖图断言）。另加一条硬边界：**`apps/server/package.json` 不得出现 vitest / vite / esbuild**（vitest 只作 `packages/shared` 的 devDep、只被前端 CI 消费），由 CI grep 兜。

**已确认的口径要点（可先供 B1 参考）**

- ⑤ pnpm **11.28.6**（`latest-11`；11.28.7 属 `next-11` 通道不取）。实测 engines `node >=22.13`、bin 为 Node 脚本、optionalDependencies 0。否决 pnpm **12.14.0**（Rust 原生重写，bin shim 原文写明找不到二进制就 *downloads one*，14 个 `@pnpm/exe.*` 平台包，离线环境直接失败且无 Node 侧兜底）；否决 npm（无 per-package 构建脚本批准、无 catalog、monorepo 治理弱）；否决 Yarn Berry（PnP 改变 node_modules 物理形态，与 Vite/Tailwind content 扫描、Playwright、verdaccio 的组合无验证预算）。root 必须写 `packageManager: "pnpm@11.28.6"` 且 workspace 的 `pmOnFail: error`（默认值为 `download`，离线环境必须改成显式失败）。**配置落 `pnpm-workspace.yaml` 而非 `.npmrc`（pnpm 11 模型）**：`allowBuilds: { esbuild: true, "@scarf/scarf": false }`（取代 `onlyBuiltDependencies`）+ `autoInstallPeers: false` + `strictDepBuilds: true` + `minimumReleaseAge: 1440`
- ⑥ ESLint **9.39.5** flat config + typescript-eslint **8.72.0** + prettier **3.9.10**；否决 ESLint 10（`eslint-plugin-react` 最新 7.37.5 的 peer 上限是 `^9.7`，且 v10 移除了 `context.getSourceCode()` 等自定义规则 API，而我们**必须**写自定义规则）。三条 P0 落工具层：`wo/no-emoji`（覆盖 Literal/TemplateElement/JSXText/JSXAttribute/注释）、`wo/no-hardcoded-color`（hex 与 rgb/hsl 函数，例外仅 #fff/#000，白名单为 tokens 生成物）、`no-restricted-imports`（拦截一切第二图标源）。规则自带 RuleTester 单测——规则自己写错是最致命的失效模式
- ⑦ 目录 `apps/web` + `apps/server` + `packages/shared` + `packages/config`；`packages/shared` 的 `dependencies` **只允许 zod**；shared 含运行时代码故需构建（tsc 两遍产出 esm + cjs，**不引入 tsup/rollup**）；不引入 turbo（`@turbo/linux-arm64-musl` 实测不存在，arm64 只有 glibc 一支）与 Nx（概念面过重，3~4 个包收益≈0）。**复评触发器**：workspace 包数 >8 或 CI 单次构建 >10 分钟或出现包级依赖图环

### 5.4 定稿补遗（评审会收尾轮的五处修订）

1. **schema 命名逐字对齐 openapi**：契约 schema 9 个，名称不得自造——`LoginRequest`(openapi:1039) / `RefreshRequest`(1065) / `UserCreateRequest`(1129) / `UserUpdateRequest`(1152) / `SsoCallbackRequest`(1167) / `SsoConfig`(1180) / `FileCreateRequest`(1193) / `FileRenameRequest`(1202) / `ShareCreateRequest`(1284)。「DTO 类名 ≡ components.schemas 键名」这条 G1 硬约定要靠命名对齐才成立。非契约 schema（FileListQuery / UserListQuery / AuditLogQuery / ExportQuery / PathParams / PasswordRules）**统一放 `src/schemas/internal/` 子目录**，G1 只比对顶层契约层——目录即分类，不靠文件头注释自律。**（就地勘误 2026-10-22：本项括注的 openapi 行号为评审会当日实测，yaml 经 8 项放行落盘后已全部漂移——LoginRequest 1039→1162、RefreshRequest 1065→1189、UserCreateRequest 1129→1254、UserUpdateRequest 1152→1278、SsoCallbackRequest 1167→1294、SsoConfig 1180→1308、FileCreateRequest 1193→1322、FileRenameRequest 1202→1332、ShareCreateRequest 1284→1415。**规约：定位一律按 schema 名 grep，任何文档不引用 openapi 行号**；D1-13 卡已按此执行。本条即挑刺 P2-3（行号漂移）在裁决记录侧的对应勘误——此前只修了卡，出处本体未修）**
2. **field 取值规约最终版**：`field = z.core.toDotPath(issue.path) || '(root)'`。两处修正——① 弃用 `join('.')`：`['rows',1,'cells',0]` 用 join 给 `rows.1.cells.0`（RHF 认不出），toDotPath 给 `rows[1].cells[0]`；含连字符键 `['a-b']` 用 join 有歧义。② **根级 issue 一律 `'(root)'`**，不区分 code：除 `unrecognized_keys` 外，请求体整体类型错（`invalid_type`，body 传数组/字符串/null）的 `path` 同样是空数组，只判 `unrecognized_keys` 会漏这一类。前端单判据 `field === '(root)'` → Toast。`rule` 保留取 `issue.code`（11 个字面量之一）作为不依赖 field 取值约定的语义信号。
3. **测试分层 L1 拆两块**：L1a 契约夹具走 `packages/shared/scripts/fixtures-run.mjs` **零依赖纯 node 脚本**，前后端 CI 执行同一条命令（后端不能装 vitest——其 peer `vite ^6.4||^7||^8` 会把 esbuild/rollup 原生二进制拉进后端依赖树，触发信创四象限核验）；L1b 非夹具纯逻辑（导入导出转换纯函数、fnv1a32、oplog/seq 工具、错误码映射）走 vitest 5.0.5 node 环境、仅前端 CI。配套硬边界：**`apps/server/package.json` 不得出现 vitest / vite / esbuild**，CI grep 兜。
4. **孤儿 schema 与快照端点**：`SnapshotSaveRequest`（openapi:1263-1266）契约描述已写明「已废弃，任何实现不得接受客户端快照上传」，故「在端点上引用」违反契约，**只剩删除一条路**。G1 对「无任何端点 `$ref` 的 components.schemas」一律 fail、不留 warn 档。配套两条机检：前端 V-S3（`apps/web/src/**` 内对 `/api/v1/files/*/snapshot` 的调用不得带 body——注意 POST 本身是合法的「触发服务端物化」端点，被契约封死的是带请求体的客户端上传）；后端 `validation-coverage.e2e-spec.ts` 反断言（POST 空 body → 200/2005，**不得** 7001）。
5. **一条被撤回的建议（纪律实例）**：评审过程中曾出现一条「DNS 缓存」运维建议，因**无任何出处**被撤回，未进入任何文档或 D1 卡。记录在此作为纪律实例——本项目对依赖、版本、运维建议一律要求「无出处不入库」，这条对 team-lead 同样适用。
