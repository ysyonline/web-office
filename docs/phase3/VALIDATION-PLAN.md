# 验证优先排期 v2.0（单人 + AI 结对）

> 状态：v2.0 ｜ 2026-10-25 ｜ 相对 v1.0 只改三样：**估算单位、架构形状、流程负担**；假设 H1~H5（见 v1.0 §1）与三条不可偷懒的形状不变。触发：用户明确约束「一个人 + AI 写代码，没有前后端分工」。

## 0. 约束变了，三条估算前提随之失效

| 约束事实（已核实） | 它推翻的东西 |
|---|---|
| 单人 + AI，无前后端分工 | **「人日」这个单位**。它假设一个人类按 6h/天连续产出；实际产出单位是**一次会话** |
| 前端本体为空：`apps/web` 仅 1 个 `index.ts`，无 Vite / 无 React / 无 `main.tsx`，Univer 未安装 | v1.0 的 S1「2 人日」不可信——它不是「接引擎」，是**从零立前端** |
| 没有第二个人 | 评审、交接类流程全部变成纯成本；同时失去唯一的错误拦截网 |

**实测口径**（不是估算）：项目历史 34 次会话，`scripts/session-effort.py` 测得并集活跃 **33.62h**；同期已交付 70 包估时合计 **81.4h**。⇒ 换算系数 **k ≈ 0.41**，即估时工时为实际活跃的约 2.4 倍。会话活跃中位数 **约 1.0h**。

两个结论：

1. **单位换成会话块（SB）**：一块 = 一次会话能闭合的可演示增量。实测中位 1h，排期按 2h 上限取。
2. **不再按人日排**。按人日排出的「16 人日」会被读成「16 个工作日」；实测同等工作量约 39h 活跃，也就是一周多。单位错了，计划的用途就没了。

> 诚实标注：33.62h 含设计卡与规划工作，不只 70 包代码，故 k=0.41 是**上界**（纯代码的 k 更低）。用于量级排期足够，用于对外承诺不够。

## 1. 架构形状：把后端推迟到 S3

「没有前后端分工」在本计划里落成一条硬规则：**能不写服务端就不写**。

| 切片 | 需要服务端 | 存储 |
|---|---|---|
| S0 打开就能编 | 否 | 硬编码 |
| S1 引擎行为 | 否 | 硬编码 |
| S2 刷新不丢 | 否（先） | IndexedDB 实现 `DataSource` |
| S3 两人同编 | **是，一个进程** | 同进程 + SQLite 文件 |
| S4 真实文件进出 | 否 | 同上 |
| S5 给别人用 | 是（复用 S3 进程） | 同上 |

三条配套决策：

1. **数据库用 SQLite**（`better-sqlite3`），不用 PG。本机无 `psql`、无 Docker、无 5432 监听；SQLite 一文件一 `require`，零安装。§4 纪律已允许（「允许先跑 SQLite 或 PG」）。
2. **`DataSource` 接口在 S2 就先定**，IndexedDB 与 HTTP 两个实现并存。这样 S2 不白做，切服务端只换实现、不动业务调用点。
3. **部署态单进程**：`apps/server` 已有 Nest 骨架（33 文件）继续当 API + WS 宿主，生产态静态托管前端产物；dev 态 Vite 5173 + 3000 两端。**S3 之前不新增 module。**

## 2. 切片与会话块

判据仍是演示动作。一个 SB = 一次会话；收口物 = 能跑的代码 + 一次 commit + 一行欠账。

| 切片 | 演示动作（收口时当场做） | SB | 卡点（单人特有） |
|---|---|---|---|
| **S0 立前端** | 浏览器打开出现表格，能改格、能求和重算 | 2 | Univer 未装；Vite/React 从零；`tsconfig` 的 `types: []` 要还原 |
| **S1 引擎行为** | 样式 / 合并 / 数字格式在真实数据上不崩 | 1 | ADR-003 被安全策略拦读，规格只能靠实测确认 |
| **S2 刷新不丢** | 改 → 自动存 → F5 → 内容与滚动位置都在 | 2 | `DataSource` 抽象必须先定，否则白做 |
| **S3 两人同编** | 两个 tab 改同一格不冲突、光标可见、刷新重连不丢 | 3 | 协议形状不可简化（§4 纪律 1） |
| **S4 真实文件进出** | 导入真实业务 xlsx 不崩 → 导出能被 Excel 打开 | 2 | 格式细节无内部规格来源，只能对着文件试 |
| **S5 给别人用** | 把链接发给别人，他自己打开就能改 | 1 | 登录已砍出本切片 |

**合计 11 SB ≈ 11–22h 活跃 ≈ 1–2 周**（每天 1–2 SB）。

对比 v1.0 的 16 人日，日历长度接近，但两处差别是本质的：

- **首个可见物从「3.5 周后」变成「第 2 个 SB 之后」**，因为 S0 只依赖前端，不需要后端、不需要数据库、不需要金仓。
- **登录被砍出 S5**。账号体系不验证任何一条假设，它只是流程；H5「陌生人体感」用一条可分享 URL 就能测。

## 3. 流程税：停四样、留三样、加两样

单人无接手人，为交接而生的文档在验证期是纯支出。**停的是维护动作，不删文件。**

| 停 | 理由 |
|---|---|
| handoff 交接件 | 没有第二个人接手；上下文靠切片卡 + `git log` |
| `ANCHORS.md` 逐包填 | 788 包锚点是交付层资产；写一条锚点的时间够写一行代码 |
| `backlog.csv` 逐包状态回写 | 只记「本切片覆盖哪几个包」一行，不逐包改状态 |
| `RELEASE-PLAN` 重生成 | 总量账冻结在 788 包 / 881.9h，不再跟随 |

| 留 | 理由 |
|---|---|
| 每 SB 一次 commit | 唯一回滚点，也是 AI 失忆后的恢复点 |
| `verify` 的 lint + typecheck | 单人没有第二双眼睛，这两段是唯一自动拦截 |
| 欠账一行 | 唯一防「演示好看、交付欠账」的闸门 |

| 加 | 理由 |
|---|---|
| 切片卡（1 页 / SB） | AI 的跨会话记忆载体，格式见 §4 |
| 「下次开工第一句」一行 | 每次会话结束留，因为 AI 不记得上次 |

## 4. 切片卡：单人 + AI 的真正瓶颈是规格可达性

上一轮 P3-012-04 卡住的真实原因不是代码难，是 `ERROR_LAYER_MATRIX` 的逐码逐列取值只在被安全策略拦读的设计卡里，AI 取不到，只能编——而编一份像样的矩阵比空着更坏（前端会照着实现）。

**团队里规格在人脑子里，AI 没有脑子。** 所以每张卡必须先做一次「规格搬运」：

```
# SB-xx <一句话目标>

## 演示动作（收口时必须当场做）
1. ...
## 规格（从设计卡 / ADR / 接口契约摘抄，AI 可直接用）
- ...（字段、约束、码值、协议形状逐条列，不写「见 D1-xx」）
## 允许硬编码 / 允许不做
## 不许碰（碰了是重写，不是补齐）
## 完成判据
- [ ] 演示动作全部可做
- [ ] verify 的 lint + typecheck 绿
- [ ] 欠账已写
## 下次开工第一句
<一行>
```

**硬规则：卡里出现「见 D1-xx」即视为卡未完成**——AI 读不到那张卡，等于没有规格。

## 5. 停止条件（不变）

- 每切片末：能演示 + 欠账已登记，缺一不算完成。
- **S5 之后必须停**：找一个真实用户（非自己、非同事）30 分钟，不提示、不代操作。通过才进产品化；不通过就改假设，**不加功能**。
- 技术可行只是三种验证之一：它能证明「做得出来」，不能证明「有人要」。

## 6. 后置项与激活条件

清单与激活条件见 v1.0 §4，未变。唯一建议**现在就做**的仍是 `RETURNING` 方言补丁，但它不阻塞任何 SB（S2 用 SQLite 起步），可在 S3 之前任意时刻插入。
